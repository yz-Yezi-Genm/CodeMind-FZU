## 四、片段与文件同版本的数据库约束

v1.2的SQL和SQLAlchemy表定义已包含下列结构，本PR补充其设计依据；以下为现有结构的等价摘录，不是应重复执行的迁移脚本：

```sql
-- document_files表内：
id UUID NOT NULL,
version_id UUID NOT NULL,
PRIMARY KEY (id),
UNIQUE (id, version_id),
FOREIGN KEY (version_id) REFERENCES document_versions (id) ON DELETE RESTRICT

-- knowledge_chunks表内：
version_id UUID NOT NULL,
file_id UUID NOT NULL,
original_file_id UUID, -- 原件未定位时允许为空
FOREIGN KEY (version_id) REFERENCES document_versions (id) ON DELETE RESTRICT,
FOREIGN KEY (file_id, version_id)
  REFERENCES document_files (id, version_id) ON DELETE RESTRICT,
FOREIGN KEY (original_file_id, version_id)
  REFERENCES document_files (id, version_id) ON DELETE RESTRICT
```

例如文件F1属于V1，写入`(file_id=F1, version_id=V2)`时，即使F1和V2各自存在，也找不到同一行`document_files(F1,V2)`，数据库会拒绝插入或更新。父表组合唯一键使该字段组可被复合外键引用。单独给`file_id`和`version_id`各加一个外键无法保证二者同版本。

`file_id`与`version_id`均NOT NULL，因此必需的来源关联不能通过NULL绕过。`original_file_id`允许NULL，默认MATCH SIMPLE语义只允许暂缺原件定位；一旦填入，`(original_file_id, version_id)`也必须匹配同版本文件。这里不能使用MATCH FULL，否则“已知版本、原件暂缺”的合法状态会被拒绝。引用中的文件及版本删除采用RESTRICT，更新也不能破坏已有引用。

ORM须保留`UniqueConstraint('id', 'version_id')`及两个`ForeignKeyConstraint`，片段的`file`关系使用`file_id`和`version_id`共同关联，不能在迁移或映射中退化成仅按文件id关联。数据库约束约束所有写入路径，不依赖单一导入脚本的判断。

复合外键只保证关联存在且同版本；原件文件角色、原文定位是否准确、来源链是否成环、正文与政策语义是否一致，仍需服务事务和人工核验。不能仅凭约束通过就宣称定位或官方核验已完成。
