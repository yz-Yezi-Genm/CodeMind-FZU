## 1. 交付结论

本说明书在丁晓炜 6 个核心实体知识库概念模型的基础上，提出完整的 23 表逻辑及物理设计，覆盖原知识库资料、版本、文件、适用规则、检索片段，以及业务方向标签、核查记录与待办任务、用户交互会话、Agent 任务执行历史、任务结果、回答引用溯源、办理节点里程碑、多文件派生来源与用户反馈闭环。

**技术基线与协同确认**：
- **候选技术基线**：本版以 **PostgreSQL 16** 和 **SQLAlchemy 2.0**（声明式映射）作为数据库详细设计与建模验证的候选技术基线。该技术选型已与技术架构负责人（赵紫龙）对接确认，作为详细设计阶段的规范依据；目前仍属设计方案，不代表 CodeMind-FZU v1.0 生产环境已绑死该部署方案。
- **概念模型协同确认**：已与概念设计负责人（丁晓炜）完成双向确认，正式采纳并固化五大业务方向的标准顺序（1.政策与事务办理、2.升学与就业发展、3.竞赛与科研信息、4.学院资源导航、5.个人成长档案与长期规划），确认 6 核心实体向 23 张扩展表的无缝映射与同版本复合外键约束。详见《[架构与概念设计确认说明_v1.2.md](架构与概念设计确认说明_v1.2.md)》。

## 3. 数据组织与架构设计

1. **核心主线**：知识分类（`knowledge_categories`）→ 知识文档（`knowledge_documents`）→ 文档版本（`document_versions`）形成主线，版本关联原始网页、附件、正文稿、整理稿（`document_files`）。附件数量不增加资料登记条数。业务方向（`business_directions`）通过多对多关联表（`document_business_directions`）实现多标签映射，不改变原主分类。
2. **同版本强约束**：通过组合唯一键与复合外键，严格保证 `(file_id, version_id)` 与 `(original_file_id, version_id)` 必须从属于同一版本，从数据库底层物理防止跨版本错挂。
3. **核查与闭环**：核查记录（`verification_records`）只追加不覆盖，核查待办（`verification_tasks`）统一管理；助手回答支持多轮引用追溯（`result_citations`），用户反馈（`answer_feedback`）可直接联动转入核查待办，形成反馈闭环。
4. **办理节点与时间精度**：通过 `document_milestones` 结构化记录多个办理节点、日期/时刻/未知精度、时区及原文，避免将单一日期作为唯一筛选入口。
