### 3. 同版本复合外键设计确认
- **约束定义**：
  - 核心实体与派生实体之间严格实施同版本约束：
    - `knowledge_chunks`: `(file_id, version_id) → document_files(id, version_id)`
    - `knowledge_chunks`: `(original_file_id, version_id) → document_files(id, version_id)`
    - `document_file_sources`: `(file_id, version_id) → document_files(id, version_id)`
    - `document_file_sources`: `(source_file_id, version_id) → document_files(id, version_id)`
    - `result_citations`: `(chunk_id, version_id) → knowledge_chunks(id, version_id)`
- **确认结论**：双方一致确认上述复合外键强约束必要且合理，能够从数据库底层杜绝跨版本引用的逻辑漏洞。

## 二、 与技术架构负责人（赵紫龙）的技术基线确认

### 1. 候选技术基线定义
- **选型方案**：以 **PostgreSQL 16** 作为目标关系型数据库方言，以 **SQLAlchemy 2.0 命令式映射（`registry.map_imperatively`）** 作为 ORM 映射规范。
- **设计成果**：在此技术基线上，已完成了 23 张表的 DDL（`sql/01_schema.sql`）、全量字段数据字典（`data-dictionary/`）、以及可导入的命令式 ORM 模型源码（`source/models.py`）。
- **字段与状态处理**：UUID 主键统一由应用层/ORM 调用端生成；`updated_at` 由业务服务显式维护，未在数据库层面配置自动更新时间触发器。

### 2. 实施边界与环境解耦声明
- **设计规范不等于生产锁定**：
  - 明确声明当前 PostgreSQL 16 + SQLAlchemy 2.0 属于**数据库详细设计与建模验证阶段的候选技术基线**，旨在保障数据结构的严谨性与约束完备性。
  - 该设计成果不代表 CodeMind-FZU v1.0 首版生产部署已强制锁定该技术栈。若后续系统技术架构根据轻量化部署需求调整生产方案（例如采用嵌入式数据库或外部统一 API 服务），本设计的关系模型、字段定义及业务规则仍具备完全的可移植性。
- **未连接实库与未部署声明**：
  - 当前成果已通过本地 SQLite 内存数据库的可移植性约束验证及 PostgreSQL AST 语法解析（303 条 DDL 语句语法 100% 通过），并由 21 项自动化单元测试覆盖。
  - 但目前尚未连接任何远端生产数据库，未执行线上部署，未接入真实前端与 Agent，符合设计阶段的交付规范。
