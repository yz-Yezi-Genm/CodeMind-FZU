## 一、 与概念设计负责人（丁晓炜）的双向对接与确认

### 1. 业务方向顺序修订正式确认采纳
- **背景说明**：在最初的 v1.0/v1.1 资料归类中，第三与第四项业务方向存在局部顺序倒置。丁晓炜在 PR #5（commit `9cbac28`）的《详细设计对接说明》中修正了该顺序并提供了初始化生成源，保留“待王智洋确认采纳”标记。
- **确认结论**：
  - 王智洋在本次数据库详细设计交付中，**正式确认并全面采纳**五大业务方向的标准顺序：
    1. `POLICY_AFFAIRS`（政策与事务办理）- `sort_order: 1`，首版核心支持
    2. `EDUCATION_CAREER`（升学与就业发展）- `sort_order: 2`，首版核心支持
    3. `COMPETITION_RESEARCH`（竞赛与科研信息）- `sort_order: 3`，首版核心支持
    4. `COLLEGE_RESOURCES`（学院资源导航）- `sort_order: 4`，首版核心支持
    5. `GROWTH_PLANNING`（个人成长档案与长期规划）- `sort_order: 5`，后续迭代功能（`future`）
  - 该顺序已在 `sql/02_review_seed_44.sql`、`knowledge-base/入库预览_44条.json`、`source/models.py` 及自动验证脚本 `validate_deliverables.py` 的强类型断言中全量固化，消除了主分支遗留的待确认状态。

### 2. 6 个核心实体向 23 张业务扩展表的演进一致性确认
- **模型对应**：
  - 丁晓炜的概念模型精准刻画了知识库业务的 6 大核心实体（`knowledge_categories`、`knowledge_documents`、`document_versions`、`document_files`、`applicability_rules`、`knowledge_chunks`）。
  - 王智洋在详细设计中保留这 6 大核心实体的全部业务语义与字段主键映射，并根据系统功能需求扩展至 23 张表（补充了业务方向多标签、资料核查历史与待办任务、用户交互会话、Agent 任务与结果历史、多轮引用追踪、办理节点里程碑、多文件派生来源及反馈闭环）。
- **确认结论**：双方确认同名实体在概念层与物理层保持 100% 对应；扩展表作为下游执行支持，完全兼容上游概念模型。

### 3. 同版本复合外键设计确认
- **约束定义**：
  - 核心实体与派生实体之间严格实施同版本约束：
    - `knowledge_chunks`: `(file_id, version_id) → document_files(id, version_id)`
    - `knowledge_chunks`: `(original_file_id, version_id) → document_files(id, version_id)`
    - `document_file_sources`: `(file_id, version_id) → document_files(id, version_id)`
    - `document_file_sources`: `(source_file_id, version_id) → document_files(id, version_id)`
    - `result_citations`: `(chunk_id, version_id) → knowledge_chunks(id, version_id)`
- **确认结论**：双方一致确认上述复合外键强约束必要且合理，能够从数据库约束层杜绝跨版本引用的逻辑漏洞。

## 二、 与技术架构负责人（赵紫龙）的技术基线确认

### 1. 候选技术基线定义
- **选型方案**：以 **PostgreSQL 16** 作为目标关系型数据库方言，以 **SQLAlchemy 2.0** 声明式模型（`Mapped` / `mapped_column`）作为 ORM 映射规范。
- **设计成果**：在此技术基线上，已完成了 23 张表的完整 DDL（`sql/01_schema.sql`，包含 UUID 主键生成、Check 约束、触发器及 `updated_at` 审计字段）、全量字段数据字典（`data-dictionary/`）、以及可导入的 ORM 模型源码（`source/models.py`）。

### 2. 实施边界与环境解耦声明
- **设计规范不等于生产锁定**：
  - 明确声明当前 PostgreSQL 16 + SQLAlchemy 2.0 属于**数据库详细设计与建模验证阶段的候选技术基线**，旨在保障数据结构的严谨性与约束完备性。
  - 该设计成果不代表 CodeMind-FZU v1.0 首版生产部署已强制锁定该技术栈。若后续系统技术架构根据轻量化部署需求调整生产方案（例如采用嵌入式数据库或外部统一 API 服务），本设计的关系模型、字段定义及业务规则仍具备完全的可移植性。
- **未连接实库与未部署声明**：
  - 当前成果已通过本地 SQLite 内存数据库的可移植性约束验证及 PostgreSQL AST 语法解析（303 条 DDL 语句语法 100% 通过），并由 18 项自动化单元测试覆盖。
  - 但目前尚未连接任何远端生产数据库，未执行线上部署，未接入真实前端与 Agent，符合设计阶段的交付规范。
