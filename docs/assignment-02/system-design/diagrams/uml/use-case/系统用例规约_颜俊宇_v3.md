# CodeMind-FZU 系统用例规约

**项目**：CodeMind-FZU（福州大学计算机学院本科生的校园事务与发展信息查询助手）
**负责人**：颜俊宇
**版本**：v3.4
**日期**：2026-11-09

---

## 一、系统边界

本系统（CodeMind-FZU）的职责边界是：**为学院本科生提供有官方来源、可追溯的校园事务与发展政策信息查询**。系统不替代学校/学院的官方发布渠道，也不做个性化升学规划、个人成长档案、动态机会推送及经验帖类 UGC 内容。

整体规划五大业务方向，对应首版（v1.0）的查询目标如下：

| 业务方向 | 首版（v1.0）范围 |
|---|---|
| 政策与事务办理 | 官方资料查询（奖学金、评优、申请条件与办理流程） |
| 升学与就业发展 | 推免规则查询（推免政策、升学要求、发展规划） |
| 竞赛与科研信息 | 竞赛认定查询（竞赛认定、赛事信息、科研机会） |
| 学院资源导航 | 学院官方资料查询（实验室、导师方向、本科生科研资源） |
| 个人成长档案与长期规划 | v2.0 及以后，后续迭代方向 |

**首版优先支持前四个方向中有官方资料依据的查询与导航**；第五个方向（个人成长档案与长期规划）为后续迭代，不纳入首版必要交付。

**三个代表性测试任务**——竞赛认定（类别及证明材料）、奖学金申请（条件与流程）、推免基本条件——仅用于验证共用的 Agent 流程，不代表业务方向数量。

## 二、参与者（角色）

| 参与者 | 角色定位 | 说明 |
|---|---|---|
| **学生（查询者）** | 查询者 | 学院本科生，以自然语言查询事务与政策信息，是系统的核心用户 |
| **知识库管理员（内容维护者）** | 内容维护者 | 负责领域知识库资料的收录、更新、归档，以及来源与时效的核验、索引构建与发布 |

> 参与者是「角色」而非「部门」。同一自然人可扮演不同角色；系统不依赖部门组织，只依赖角色权限。

## 四、关键用例规约

### UC-01 查询竞赛认定信息

- **编号**：UC-01
- **参与者**：学生（查询者）
- **前置条件**：学生已进入系统查询界面；知识库中已收录竞赛认定相关官方资料。
- **触发事件**：学生提出某项竞赛的认定问题（如「XX 竞赛在学院如何认定、对综测和推免有何影响」）。
- **主成功场景**：
  1. 学生输入竞赛认定问题；
  2. 系统理解意图，检索竞赛认定规则；
  3. 系统核验资料来源、版本与时效；
  4. 系统展示认定类别、认定规则要点及对综测/推免的影响，并附官方来源；
  5. 学生获得有依据、可追溯的回答。
- **扩展流程**：
  - **1a. 信息不足**：系统无法确定学生年级/专业/具体竞赛 → 追问必要信息，学生补充后继续（信息最小化，仅用于本次回答）。
  - **3a. 证据不足**：未检索到相关官方资料 → 系统明确说明「无官方依据」，建议线下咨询学院，不编造结论。
  - **3b. 版本冲突/时效未确认**：存在多个版本或资料过期 → 系统如实标注冲突与时效，提示以最新官方通知为准。
  - **4a. 查看依据**：学生点击查看回答所引用的来源部门、日期、链接与核验状态。
- **后置条件**：学生获得有来源可核对的回答，或明确的「无法作答」提示及线下核实建议。

### UC-02 查询奖学金申请信息

- **编号**：UC-02
- **参与者**：学生（查询者）
- **前置条件**：知识库已收录奖学金、评优相关的官方政策与申请流程资料。
- **触发事件**：学生询问某类奖学金的申请条件、所需材料、时间节点或办理流程。
- **主成功场景**：
  1. 学生输入奖学金申请相关问题；
  2. 系统理解意图，检索奖学金/评优政策与办理流程；
  3. 系统核验资料来源、版本与时效；
  4. 系统展示申请条件、材料清单、时间节点与办理流程，并附官方来源；
  5. 学生获得有依据、可追溯的申请指导信息。
- **扩展流程**：
  - **1a. 信息不足**：系统无法确定学生年级/专业/具体奖项 → 追问必要信息后继续。
  - **3a. 证据不足**：未检索到相关官方资料 → 明确说明「无官方依据」，建议线下咨询学院。
  - **3b. 版本冲突/时效未确认**：政策已更新或存在多版本 → 如实标注，提示以最新官方通知为准。
  - **4a. 查看依据**：学生点击查看回答所引用的来源部门、日期、链接与核验状态。
- **后置条件**：学生获得奖学金申请条件、材料与流程的明确答案及来源。

### UC-03 查询推免条件

- **编号**：UC-03
- **参与者**：学生（查询者）
- **前置条件**：知识库已收录推免政策及学院实施细则。
- **触发事件**：学生询问推免的政策要求、成绩要求或适用范围。
- **主成功场景**：
  1. 学生输入推免政策相关问题；
  2. 系统检索推免政策与学院实施细则；
  3. 系统核验资料时效（区分「最新政策」与「历史政策」）；
  4. 系统展示成绩要求、加分项、关键时间节点与适用范围，并附来源；
  5. 学生了解政策要求与适用范围。
- **扩展流程**：
  - **1a. 信息不足**：缺少目标专业/年级/具体政策范围 → 追问后继续。
  - **3a. 政策未更新**：仅有历史政策 → 明确标注「可能已更新，以最新通知为准」。
  - **4a. 查看依据**：学生点击查看回答所引用的来源与核验状态。
- **后置条件**：学生获得推免政策、成绩要求与适用范围的明确答案及来源。
- **功能边界**：本用例只解释官方政策、成绩要求与适用范围，**不要求用户提供成绩排名，也不预测或判断用户是否具备推免资格**。

### UC-04 查询学院资源信息

- **编号**：UC-04
- **参与者**：学生（查询者）
- **前置条件**：知识库已收录学院官方资源资料（实验室、导师方向、本科生科研资源等）。
- **触发事件**：学生询问实验室方向、导师研究领域、本科生科研资源或学院办事渠道等官方资源信息。
- **主成功场景**：
  1. 学生输入学院资源相关问题；
  2. 系统检索学院官方资源资料；
  3. 系统核验资料来源与时效；
  4. 系统展示资源信息与办事渠道，并附来源；
  5. 学生获得有来源、可追溯的资源导航信息。
- **扩展流程**：
  - **1a. 信息不足**：缺少具体方向/专业 → 追问后继续。
  - **3a. 证据不足**：未检索到相关官方资料 → 如实说明并建议线下咨询学院。
  - **4a. 查看依据**：学生点击查看回答所引用的来源与核验状态。
- **后置条件**：学生获得学院资源的查询与导航信息及来源。

### UC-05 维护知识库资料

- **编号**：UC-05
- **参与者**：知识库管理员（内容维护者）
- **前置条件**：管理员具有知识库维护权限，能够访问资料维护与索引发布流程。
- **触发事件**：新资料发布，或现有资料需要更新/归档。
- **主成功场景**：
  1. 管理员新增、更新或归档资料；
  2. 管理员补充资料的来源部门、发布日期、链接；
  3. 管理员执行「核验资料时效与来源」（UC-06，见下）；
  4. 通过核验的资料进入索引构建与质量检查；
  5. 质量检查与离线测试通过后，经人工审核完成版本发布；
  6. 资料随完整版本正式上线，进入可检索状态。
- **扩展流程**：
  - **1a. 资料冲突**：新资料与旧资料内容冲突 → 保留两个版本，标注差异与时效，不直接覆盖。
  - **4a. 质量/测试未通过**：质量检查或离线测试未通过 → 发布中止，构建中的版本不进入检索，保留上一版完整可用版本。
  - **5a. 发布失败**：版本切换失败 → 回滚并保留上一版可用版本，查询侧始终只读取完整发布版本。
- **后置条件**：只有通过核验、质量检查、测试与人工审核的完整版本才切换上线；知识库内容更新且可被查询类用例检索，失败时上一版仍可用。

### UC-06 核验资料时效与来源

- **编号**：UC-06
- **参与者**：知识库管理员（内容维护者）
- **前置条件**：存在待核验的知识库资料；管理员具有核验权限。
- **触发事件**：新资料入库后需要核验，或现有资料需要复核来源与时效。
- **主成功场景**：
  1. 管理员逐条核验资料来源（发布部门、官方渠道），更新**来源核验状态**；
  2. 管理员核验资料发布日期与适用时间范围，更新**时效核验状态**；
  3. 管理员确认资料所属的**政策生命周期状态**（当前有效 / 已废止 / 部分适用等）；
  4. 系统更新对应状态字段，已废止或过期的资料标记为历史参考。
- **后置条件**：资料的来源核验状态、时效核验状态与政策生命周期状态分别明确记录，作为索引构建与发布的前置输入。
- **状态说明**：来源核验、时效核验与政策生命周期是三个独立维度，分别对应数据库 `document_versions` 中的 `source_verification_status`、`timeliness_verification_status` 与 `policy_status` 字段，不互相混用。

### UC-07 补充信息追问（扩展用例）

- **编号**：UC-07
- **参与者**：学生（查询者）
- **前置条件**：学生已发起查询（基用例「查询校园事务信息」执行中）。
- **触发条件**（扩展条件）：系统判断信息不足（如缺少年级、专业、目标用途、具体竞赛名称），无法给出精准回答。
- **主成功场景**：
  1. 系统向学生追问必要信息；
  2. 学生补充作答；
  3. 系统据此组织更精准的回答。
- **后置条件**：补充的信息用于本次回答（信息最小化，不额外留存），回答精度提升。

### UC-08 查看回答依据（扩展用例）

- **编号**：UC-08
- **参与者**：学生（查询者）
- **前置条件**：学生已获得回答（基用例「查询校园事务信息」执行中）。
- **触发条件**（扩展条件）：学生想核实回答的官方来源。
- **主成功场景**：
  1. 学生点击查看回答依据；
  2. 系统展示来源部门、发布日期、链接与核验状态；
  3. 学生据此判断回答可信度。
- **后置条件**：学生能追溯回答的官方依据，实现「回答可追溯」。

### UC-09 反馈回答问题

- **编号**：UC-09
- **参与者**：学生（查询者）
- **前置条件**：学生已获得系统回答。
- **触发事件**：学生认为回答有误、依据不足或表述不清，希望反馈。
- **主成功场景**：
  1. 学生对回答发起反馈（如指出错误、缺少依据等）；
  2. 系统记录反馈内容并关联到对应回答与资料版本；
  3. 系统确认反馈已提交，并提示后续将人工复核。
- **扩展流程**：
  - **2a. 反馈信息不完整**：缺少具体问题描述 → 系统提示补充后再提交。
- **后置条件**：反馈被记录（对应 `answer_feedback`），供知识库管理员后续核验与改进资料。

## 五、关系说明

- **关联**：学生（查询者）与抽象基用例「查询校园事务信息」关联；知识库管理员与「维护知识库资料」「核验资料时效与来源」关联。
- **泛化**：4 个查询类用例（竞赛认定、奖学金申请、推免条件、学院资源信息）是抽象基用例「查询校园事务信息」的特例（空心三角实线）。
- **扩展（extend）**：「补充信息追问」「查看回答依据」在特定条件下从抽象基用例「查询校园事务信息」扩展，属于可选交互（扩展条件见各自规约的「触发条件」）。
- **包含（include）**：「维护知识库资料」包含「核验资料时效与来源」——核验是维护流程的必备环节。
- **独立触发**：「核验资料时效与来源」既可作为「维护知识库资料」的子流程被包含，也可由知识库管理员独立触发（如定期复核既有资料）。
- **抽象基用例标识**：`查询校园事务信息` 为抽象基用例，仅用于统一 4 个查询类用例的泛化关系，不独立计数为交付功能、不单独实现。

### 用例数量说明

用例图共包含 **1 个抽象基用例 + 9 个具体用例**：

- 抽象基用例：`查询校园事务信息`（仅用于统一 4 个查询类用例的泛化关系，不独立计数）；
- 具体用例 9 个：UC-01 ~ UC-09，其中学生侧 7 个（4 个查询目标 + 2 个扩展交互 + 1 个反馈）、知识库管理员侧 2 个。
