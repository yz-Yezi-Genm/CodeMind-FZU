# CodeMind-FZU 系统用例规约

**项目**：CodeMind-FZU（福州大学计算机学院本科生的校园事务与发展信息查询助手）
**负责人**：颜俊宇
**版本**：v3.1
**日期**：2026-11-08

---

## 一、系统边界

本系统（CodeMind-FZU）的职责边界是：**为学院本科生提供有官方来源、可追溯的校园事务与发展政策信息查询**。系统不替代学校/学院的官方发布渠道，也不做个性化升学规划、个人成长档案、动态机会推送及经验帖类 UGC 内容。

整体规划五大业务方向：政策与事务办理、升学与就业发展、竞赛与科研信息、学院资源导航、个人成长档案与长期规划。**首版（v1.0）优先支持前四个方向中有官方资料依据的查询与导航**；第五个方向（个人成长档案与长期规划）为后续迭代，不纳入首版必要交付。

**三个代表性测试任务**——竞赛认定（类别及证明材料）、奖学金申请（条件与流程）、推免基本条件——仅用于验证共用的 Agent 流程，不代表业务方向数量。**交换与出国交流属于「升学与就业发展」方向下的具体事项，目前资料不足，不作为首版确定交付**。

## 二、参与者（角色）

| 参与者 | 角色定位 | 说明 |
|---|---|---|
| **学生（查询者）** | 查询者 | 学院本科生，以自然语言查询事务与政策信息，是系统的核心用户 |
| **知识库管理员（内容维护者）** | 内容维护者 | 负责领域知识库资料的收录、更新、归档，以及来源与时效的核验、索引构建与发布 |

> 参与者是「角色」而非「部门」。同一自然人可扮演不同角色；系统不依赖部门组织，只依赖角色权限。

## 四、关键用例规约

### UC-01 查询竞赛认定信息

- **编号**：UC-01
- **参与者**：学生（查询者）
- **前置条件**：学生已进入系统查询界面；知识库中已收录竞赛认定相关官方资料。
- **触发事件**：学生提出某项竞赛的认定问题（如「XX 竞赛在学院如何认定、对综测和推免有何影响」）。
- **主成功场景**：
  1. 学生输入竞赛认定问题；
  2. 系统理解意图，检索竞赛认定规则；
  3. 系统核验资料来源、版本与时效；
  4. 系统展示认定类别、认定规则要点及对综测/推免的影响，并附官方来源；
  5. 学生获得有依据、可追溯的回答。
- **扩展流程**：
  - **1a. 信息不足**：系统无法确定学生年级/专业/具体竞赛 → 追问必要信息，学生补充后继续（信息最小化，仅用于本次回答）。
  - **3a. 证据不足**：未检索到相关官方资料 → 系统明确说明「无官方依据」，建议线下咨询学院，不编造结论。
  - **3b. 版本冲突/时效未确认**：存在多个版本或资料过期 → 系统如实标注冲突与时效，提示以最新官方通知为准。
  - **4a. 查看依据**：学生点击查看回答所引用的来源部门、日期、链接与核验状态。
- **后置条件**：学生获得有来源可核对的回答，或明确的「无法作答」提示及线下核实建议。

### UC-03 查询保研推免条件

- **编号**：UC-03
- **参与者**：学生（查询者）
- **前置条件**：知识库已收录推免/保研政策及学院实施细则。
- **触发事件**：学生询问保研/推免的硬性条件、成绩门槛或加分项。
- **主成功场景**：
  1. 学生输入保研条件问题；
  2. 系统检索推免政策与学院实施细则；
  3. 系统核验资料时效（区分「最新政策」与「历史政策」）；
  4. 系统展示成绩门槛、加分项、关键时间节点，并附来源；
  5. 学生了解自身条件与政策要求的差异。
- **扩展流程**：
  - **1a. 信息不足**：缺少年级/专业/成绩排名 → 追问后继续。
  - **3a. 政策未更新**：仅有历史政策 → 明确标注「可能已更新，以最新通知为准」。
- **后置条件**：学生获得保研硬性条件的明确答案及来源，并了解自身条件与政策要求的差异。

### UC-06 维护知识库资料

- **编号**：UC-06
- **参与者**：知识库管理员（内容维护者）
- **前置条件**：管理员已登录并具有知识库维护权限。
- **触发事件**：新资料发布，或现有资料需要更新/归档。
- **主成功场景**：
  1. 管理员新增、更新或归档资料；
  2. 管理员补充资料的来源部门、发布日期、链接；
  3. 管理员执行「核验资料时效与来源」（UC-07，必然包含）；
  4. 系统为通过核验的资料构建索引（Chroma 与 BM25 双索引，统一 versionId=vN）；
  5. 系统执行质量闸门（QualityGate）与离线 PoC 测试（PoCTestSuite），确认双索引均通过（PASS）；
  6. 人工审核通过后，由 IndexPublisher 提交版本，VersionRegistry 原子切换活动版本；
  7. 资料随完整索引版本正式发布，进入 Agent 可检索状态。
- **扩展流程**：
  - **1a. 资料冲突**：新资料与旧资料内容冲突 → 保留两个版本，标注差异与时效，不直接覆盖。
  - **5a. 质量/测试未通过**：质量闸门或 PoC 测试未通过 → 发布中止，构建中的索引不进入 Agent，保留上一版完整可用索引。
  - **6a. 发布失败**：版本切换失败 → 回滚并保留上一版活动索引，AgentQueryGateway 始终只读取完整发布版本。
- **后置条件**：只有通过审核、测试通过的完整索引版本才切换上线；知识库内容更新且可被查询类用例检索，失败时上一版索引仍可用。

### UC-07 核验资料时效与来源

- **编号**：UC-07
- **参与者**：知识库管理员（内容维护者）
- **前置条件**：存在待核验的知识库资料。
- **主成功场景**：
  1. 管理员逐条核验资料来源（发布部门、官方渠道）；
  2. 管理员核验资料发布日期与适用时间范围；
  3. 管理员标记核验状态（已核验 / 待核验 / 已过期）；
  4. 系统更新资料核验状态，过期资料标记为历史参考。
- **后置条件**：资料具有明确的核验状态与时效标记，作为后续索引构建与发布的前置输入，支撑「回答可追溯」原则。

### UC-08 补充信息追问（扩展用例）

- **编号**：UC-08
- **参与者**：学生（查询者）
- **前置条件**：学生已发起查询（基用例「查询校园事务信息」执行中）。
- **触发条件**：系统判断信息不足（如缺少年级、专业、目标用途、具体竞赛名称），无法给出精准回答。
- **主成功场景**：
  1. 系统向学生追问必要信息；
  2. 学生补充作答；
  3. 系统据此组织更精准的回答。
- **后置条件**：补充的信息用于本次回答（信息最小化，不额外留存），回答精度提升。

### UC-09 查看回答依据（扩展用例）

- **编号**：UC-09
- **参与者**：学生（查询者）
- **前置条件**：学生已获得回答（基用例「查询校园事务信息」执行中）。
- **触发条件**：学生想核实回答的官方来源。
- **主成功场景**：
  1. 学生点击查看回答依据；
  2. 系统展示来源部门、发布日期、链接与核验状态；
  3. 学生据此判断回答可信度。
- **后置条件**：学生能追溯回答的官方依据，实现「回答可追溯」。

## 五、关系说明

- **关联**：学生（查询者）与「查询校园事务信息」关联；知识库管理员与「维护知识库资料」关联。
- **泛化**：5 个查询类用例（竞赛认定、奖学金申请、保研推免条件、交换与出国项目信息、培养方案与选课信息）是抽象基用例「查询校园事务信息」的特例（空心三角实线）。
- **扩展（extend）**：「补充信息追问」「查看回答依据」在特定条件下从「查询校园事务信息」扩展，属于可选交互。
- **包含（include）**：「维护知识库资料」**必然包含**「核验资料时效与来源」——核验是维护与索引发布流程的必要环节。

### 用例数量说明

用例图共包含 **1 个抽象基用例 + 9 个具体用例**：

- 抽象基用例：`查询校园事务信息`（仅用于统一 5 个查询类用例的泛化关系，不独立计数为交付功能）；
- 具体用例 9 个：UC-01 ~ UC-09，其中学生侧 7 个（5 个查询目标 + 2 个扩展交互）、知识库管理员侧 2 个。
