## 1. 设计依据

本通信设计遵循第一次作业开题答辩稿已确定的方案：

- Web 前端使用 HTML、CSS、JavaScript；
- FastAPI 负责统一接口、请求管理和异常处理；
- Agent 负责任务识别、策略选择、主动追问和受控工具调用建议；
- 本地知识库使用 Embedding、Chroma 和 BM25，RRF 融合排序；
- Qwen API 理解问题并基于证据组织回答；
- Tavily 是候选联网核验工具；
- 输出前检查来源、年份、适用范围和证据可靠性。

图示中的组件属于概要设计。已有基础是 Figma 原型、44 条资料登记记录中的 43 条正文提取和 9 项离线 PoC 测试，不代表真实 Qwen、混合检索、联网服务或完整系统已经联调。

## 3. 官方资料问答通信

### 3.1 参与对象

| 对象 | 职责 |
|---|---|
| `Browser` | 学生浏览器，提交问题并展示答案、来源与状态 |
| `Frontend` | 管理页面状态，调用 `/api/ask`，渲染引用与不确定性 |
| `AskController` | FastAPI 请求校验、异常映射和响应封装 |
| `TaskRouter` | 识别事务、机会或规划任务，抽取年级、专业、年份和用途 |
| `Clarifier` | 对缺失信息提出一个最关键追问 |
| `AgentOrchestrator` | 选择检索、核验、生成和输出步骤 |
| `HybridRetriever` | 并行组织 Chroma 语义召回与 BM25 关键词召回 |
| `ChromaIndex` | 返回语义相近的本地资料分块 |
| `BM25Index` | 返回规则名称、文号、年度等精确匹配结果 |
| `RRFRanker` | 融合两路名次、去重并保留候选来源 |
| `EvidenceVerifier` | 检查来源、发布日期、适用范围、时效和结论引用 |
| `OnlineCheck` | 必要时调用 Tavily 检索官方公开信息 |
| `LLMAdapter` | 调用 Qwen API，基于证据生成结构化回答 |
| `AnswerComposer` | 补充解释、引用、限制和下一步建议 |

### 3.2 消息顺序

| 编号 | 发送方 → 接收方 | 消息与数据 | 约束 |
|---|---|---|---|
| 1 | Browser → Frontend | `submitQuestion(question, context)` | 问题非空，附带当前年级/专业等可见上下文 |
| 2 | Frontend → AskController | `POST /api/ask` | JSON 请求；返回结果带 `requestId` |
| 3 | AskController → TaskRouter | `validateAndClassify(request)` | 参数不合法时不进入 Agent |
| 4 | TaskRouter → AgentOrchestrator | `route(taskType, entities)` | 选择事务、机会或规划策略 |
| 4a | TaskRouter → AgentOrchestrator | `missingFields` | 缺少年级、专业、事项、年份或用途 |
| 4b | AgentOrchestrator → Frontend | `needs_clarification` | 只提出一个关键追问，不猜测 |
| 5 | AgentOrchestrator → HybridRetriever | `retrieve(queryPlan)` | 本地资料优先；限制 Top-K |
| 5.1a | HybridRetriever → ChromaIndex | `vectorSearch(embedding)` | Embedding 使用与索引一致的模型 |
| 5.1b | HybridRetriever → BM25Index | `keywordSearch(tokens)` | 保留关键词命中的政策名称和年度 |
| 5.2 | ChromaIndex / BM25Index → RRFRanker | `rankedCandidates` | 两路候选去重并保留原始得分或名次 |
| 6 | RRFRanker → EvidenceVerifier | `fusedEvidence` | 核对官方来源、发布日期和适用范围 |
| 6.1 | EvidenceVerifier → OnlineCheck | `verifyOfficialInfo(query)` | 可选；仅对当前动态信息使用 |
| 7 | AgentOrchestrator → LLMAdapter | `generate(question, evidence, constraints)` | 无足够证据时不调用自由生成 |
| 7.1 | LLMAdapter → EvidenceVerifier | `draft + citationIds` | 模型草稿视为不可信输入 |
| 8 | EvidenceVerifier → AnswerComposer | `validatedAnswer` | 删除无引用结论，处理版本冲突 |
| 9 | AnswerComposer → AskController | `answer, citations, status, limitations` | 统一结构化响应 |
| 10 | Frontend → Browser | `render(response)` | 展示官方来源、年份、适用范围和不确定性 |

### 3.3 响应字段

```json
{
  "requestId": "req_xxx",
  "answer": "……",
  "answerStatus": "grounded",
  "citations": [
    {
      "documentId": "competition-recognition-2026",
      "title": "关于公布大学生学科竞赛级别认定结果的通知",
      "publisher": "福州大学",
      "publishedAt": "2026-03-06",
      "policyStatus": "current_reference",
      "sourcePath": "knowledge_base/...",
      "locator": "附件第 2 页"
    }
  ],
  "limitations": [
    "该结果仅适用于当前登记版本，最新年度通知仍需核验。"
  ]
}
```

`answerStatus` 包括 `grounded`、`needs_clarification`、`insufficient_evidence`、`conflict` 和 `degraded`。

## 4. 知识资料维护与索引更新通信

### 4.1 参与对象

| 对象 | 职责 |
|---|---|
| `Maintainer` | 登记官方资料、核对元数据、运行维护流程 |
| `IngestionEntry` | 首版为维护脚本；后续可以扩展为 Web 管理端 |
| `MetadataGate` | 检查来源、发布单位、日期、适用对象、文件类型和哈希 |
| `ParserOCR` | 解析 HTML/PDF/DOCX，识别扫描件 OCR 需求 |
| `LocalKnowledge` | 保存原始资料、中文整理稿和定位信息 |
| `IndexCSV` | 更新人工可读的 CSV 元数据索引 |
| `ChunkBuilder` | 按标题层级或字符窗口分块，保留页码/段落 |
| `ChromaBuilder` | 生成 Embedding 并重建向量索引 |
| `BM25Builder` | 重建关键词倒排索引 |
| `QualityGate` | 核验来源、日期、适用范围、正文完整性和重复项 |
| `PoCTestSuite` | 运行检索、引用、冲突与无依据处理测试 |
| `MaintenanceReport` | 生成成功、失败、待 OCR 和待联网核验清单 |

### 4.2 消息顺序

| 编号 | 发送方 → 接收方 | 消息与数据 | 约束 |
|---|---|---|---|
| 1 | Maintainer → IngestionEntry | `addOfficialDocument(file, metadata)` | 只接收公开官方资料 |
| 2 | IngestionEntry → MetadataGate | `validate(source, type, size, hash)` | 来源和日期缺失时进入待补充 |
| 3 | MetadataGate → ParserOCR | `parse(documentRef)` | 保留原始文件，不覆盖旧版本 |
| 4 | ParserOCR → LocalKnowledge | `saveOriginal, extractedText, locator` | 区分原始资料与中文整理稿 |
| 5 | LocalKnowledge → IndexCSV | `upsertMetadata(record)` | 一项政策或通知计一条 |
| 6 | LocalKnowledge → ChunkBuilder | `buildChunks(text, headings)` | 分块保留页码/段落定位 |
| 7 | ChunkBuilder → ChromaBuilder | `embedAndUpsert(chunks)` | 使用固定版本的分块规则 |
| 7b | ChunkBuilder → BM25Builder | `tokenizeAndUpsert(chunks)` | 保留规则名称、文号和年度 |
| 8 | ChromaBuilder / BM25Builder → QualityGate | `indexStatus` | 任一索引失败不得标记可用 |
| 9 | QualityGate → PoCTestSuite | `runSmokeAndEvidenceTests` | 检查检索、引用与无依据处理 |
| 10 | QualityGate → MaintenanceReport | `report(status, pendingItems)` | 输出待 OCR、待核验和失败项 |
| 10.1 | MaintenanceReport → IngestionEntry | `updateSummary` | 不把“已登记”表述为“已联网复核” |

## 5. 异常与降级

| 场景 | 处理 |
|---|---|
| 问题缺少必要信息 | 返回 `needs_clarification`，不调用生成模型 |
| Chroma 不可用 | 使用 BM25 的关键词结果并标记降级 |
| BM25 不可用 | 使用语义召回，但提示精确规则匹配能力下降 |
| 两路结果分歧 | RRF 融合后核验版本和适用范围，仍冲突时返回 `conflict` |
| 证据不足 | 返回 `insufficient_evidence`，不生成确定政策结论 |
| Qwen 超时 | 返回可读的检索摘要和来源，标记 `degraded` |
| Qwen 引用不存在 | 删除对应结论；无法校正时返回证据不足 |
| Tavily 失败 | 只用本地证据；动态信息无法确认时明确提示 |
| OCR 未完成 | 在维护报告中标记，不把扫描件文本用于正式回答 |
| 索引重建失败 | 保留上一版可用索引；不发布半完成索引 |

## 6. 可信性与一致性要求

1. 每条确定结论必须关联至少一个来源记录。
2. 引用必须包含资料标题、发布单位、发布日期、适用范围和定位。
3. 年度通知和学期通知必须显式标注时效。
4. 旧版政策不得覆盖新版本，必须保留并标注状态。
5. “已登记”“已提取正文”“已向量化”“已联网核验”是四个不同状态，不得混用。
6. 模型只接收经过筛选的证据片段，不接收 API 密钥和无关个人信息。
7. Tavily 搜索结果必须回到官方原文核对，不能直接作为最终政策依据。
8. 索引重建失败时保留上一版可用索引，并报告失败项。

## 7. 数据统计口径风险

首次作业 PPT 的封面与主讲备注在样本量上存在不一致：正文部分显示 84 份有效问卷，部分演讲备注写作 21 份；正文还出现 64/84、52/84 与 76/84 等统计。该问题不影响本文的技术通信链路，但会影响项目成果中的调研可信度。

在博客、系统设计说明书和最终演示中必须统一问卷样本、分母和题目口径，不能同时传播 21 与 84 两套数据。

知识库也存在版本差异：开题稿记录 44 条资料，当前仓库 CSV 只有 31 条。合并前需要确认哪一份是最新维护版本，并同步原始文件、整理稿和索引。
