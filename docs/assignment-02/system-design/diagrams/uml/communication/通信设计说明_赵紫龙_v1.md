## 1. 设计依据

本通信设计遵循第一次作业开题答辩稿和团队最终确定的首版范围：

- Web 前端使用 HTML、CSS、JavaScript；
- FastAPI 负责统一接口、请求管理和异常处理；
- Agent 负责任务识别、策略选择、主动追问和受控工具调用建议；
- 本地知识库使用 Embedding、Chroma 和 BM25，RRF 融合排序；
- Qwen API 接收问题和证据后返回回答草稿；
- Tavily 是候选联网核验工具，查询请求和结果返回均经过 EvidenceVerifier；
- 输出前检查来源、年份、适用范围、引用与证据可靠性。

首版四个核心应用场景统一为：政策事务、推免规则、竞赛认定和学院资源。完整就业推荐、科研动态和个性化成长建议不纳入首版承诺。

图示中的组件属于概要设计。已有基础是 Figma 原型、44 条资料登记、43 条正文提取和 9 项离线 PoC 测试，不代表真实 Qwen、混合检索、联网服务或完整系统已经联调。

## 3. 官方资料问答通信

### 3.1 参与对象

| 对象 | 职责 |
|---|---|
| `Browser` | 提交问题、补充信息、展示追问和最终引用 |
| `Frontend` | 管理输入状态，调用 `/api/ask`，渲染回答与不确定性 |
| `AskController` | FastAPI 请求校验、异常映射和响应返回 |
| `TaskRouter` | 识别事务、机会或规划任务，抽取年级、专业、年份和用途 |
| `Clarifier` | 根据缺失字段生成主动追问 |
| `AgentOrchestrator` | 编排追问、检索、核验、Qwen 生成和回答组织 |
| `HybridRetriever` | 组织 Chroma 语义召回与 BM25 关键词召回 |
| `ChromaIndex` | 返回语义相近的本地资料分块 |
| `BM25Index` | 返回规则名称、文号、年度等精确匹配结果 |
| `RRFRanker` | 融合两路候选、去重并保留召回依据 |
| `EvidenceVerifier` | 核验来源、发布日期、适用范围、时效、引用和冲突 |
| `OnlineCheck` | 向 Tavily 提交查询并接收返回结果，供证据核验 |
| `LLMAdapter` | 向 Qwen 提交问题与证据，接收回答草稿 |
| `AnswerComposer` | 组织解释、引用、限制和下一步建议 |

### 3.2 成功主路径

| 编号 | 发送方 → 接收方 | 消息与数据 | 约束 |
|---|---|---|---|
| 1 | Browser → Frontend | `submitQuestion(question, context)` | 问题非空；携带当前年级、专业等信息 |
| 2 | Frontend → AskController | `POST /api/ask` | 返回 `requestId`；不暴露模型密钥 |
| 3 | AskController → TaskRouter | `validateAndClassify(request)` | 参数不合法时不进入 Agent |
| 6 | TaskRouter → AgentOrchestrator | `route(taskType, entities)` | 选择事务、机会或规划策略 |
| 7 | AgentOrchestrator → HybridRetriever | `retrieve(queryPlan)` | 本地资料优先；限制 Top-K |
| 7.1a | HybridRetriever → ChromaIndex | `vectorSearch(embedding)` | 使用与索引一致的 Embedding 模型 |
| 7.1b | HybridRetriever → BM25Index | `keywordSearch(tokens)` | 保留规则名称、文号和年度 |
| 7.2a | ChromaIndex → RRFRanker | `semanticCandidates` | 提交语义候选及其原始名次 |
| 7.2b | BM25Index → RRFRanker | `keywordCandidates` | 提交关键词候选及其原始名次 |
| 8 | RRFRanker → EvidenceVerifier | `fusedEvidence` | 两路候选融合、去重后核验 |
| 9 | AgentOrchestrator → LLMAdapter | `generate(question, evidence, constraints)` | 问题和筛选后的证据一起提交 |
| 9.1 | LLMAdapter → EvidenceVerifier | `draftAnswer + citationIds` | Qwen 返回回答草稿，不直接返回用户 |
| 10 | EvidenceVerifier → AnswerComposer | `validatedAnswer` | 检查草稿、引用和政策状态 |
| 11 | AnswerComposer → AskController | `answer, citations, status, limitations` | 只返回通过核验的内容 |
| 12 | AskController → Frontend | `finalResponse` | HTTP 响应与状态码 |
| 13 | Frontend → Browser | `render(finalResponse)` | 展示答案、来源、时效和限制 |

### 3.3 主动追问与重新提交

| 编号 | 发送方 → 接收方 | 消息与数据 | 约束 |
|---|---|---|---|
| 4a | TaskRouter → Clarifier | `missingFields` | 例如缺少年级、竞赛名称或认定用途 |
| 4b | Clarifier → AskController | `clarificationPrompt` | 生成一个最关键问题 |
| 4c | AskController → Frontend | `needs_clarification + prompt` | 返回追问状态，不调用 Qwen |
| 4d | Frontend → Browser | `showClarification(prompt)` | 保留已输入问题和上下文 |
| 5 | Browser → Frontend | `resubmitQuestion(question + supplement)` | 用户补充信息后重新提交 |
| 5.1 | Frontend → AskController | `POST /api/ask` | 关联原请求或会话 ID，重新进入流程 |

消息 4a、4b 均是“从任务识别到追问、再由追问返回 FastAPI”的方向；4c、4d 继续把追问返回前端与浏览器。用户补充后，5 和 5.1 将问题重新送入 AskController，并再次执行消息 3。

### 3.4 Tavily 与 Qwen 方向

| 编号 | 发送方 → 接收方 | 消息与数据 | 约束 |
|---|---|---|---|
| 8.1 | EvidenceVerifier → OnlineCheck | `queryOfficialSources(query)` | 只在当前动态信息需要在线核验时调用 |
| 8.2 | OnlineCheck → EvidenceVerifier | `searchResults + sourceUrls` | 返回结果不能绕过官方原文核验 |
| 9 | AgentOrchestrator → LLMAdapter | `question + filteredEvidence` | 由 Agent 提交输入，而不是由前端直连 Qwen |
| 9.1 | LLMAdapter → EvidenceVerifier | `draftAnswer + citations` | Qwen 返回草稿后由证据核验模块检查 |

### 3.5 回答状态

- `grounded`：存在足够且适用的官方证据。
- `needs_clarification`：缺少回答所必需的字段。
- `insufficient_evidence`：本地资料与可选在线核验均不足以支持确定结论。
- `conflict`：不同政策版本或规则冲突，需要展示来源并提示人工核验。
- `degraded`：Qwen 或 Tavily 不可用，只能返回检索摘要或稍后重试提示。

## 4. 知识资料维护与索引更新通信

### 4.1 知识库统计基准

知识库资料总量以开题答辩 PPT 第 06 页的 **44 条**为项目基准：

- 13 条已有部分核查记录，仍有待核项；
- 31 条已完成本地文件与来源登记核查，时效待联网复核；
- 44 条中 43 条已提取正文，1 条扫描版文件待 OCR。

当前 GitHub 仓库中的 `knowledge_base/政策资料/知识库索引.csv` 只有 **31 条现有索引记录**。这仅表示当前 CSV 的记录数量，不能把知识库总量改成 31，也不能直接认定这 31 条与上述核查状态中的 31 条完全对应。最终对应关系由知识库负责人核对后再同步。

### 4.2 参与对象

| 对象 | 职责 |
|---|---|
| `Maintainer` | 登记资料、补充元数据、处理待核项 |
| `IngestionEntry` | 首版维护脚本；后续可扩展 Web 管理端 |
| `MetadataGate` | 检查来源、发布单位、日期、适用对象、类型和哈希 |
| `ParserOCR` | 解析 HTML/PDF/DOCX，标记扫描件 OCR 需求 |
| `LocalKnowledge` | 保存原始资料、中文整理稿和定位信息 |
| `IndexCSV` | 更新当前人工可读元数据索引 |
| `ChunkBuilder` | 分块并保留页码或段落定位 |
| `ChromaBuilder` | 生成 Embedding、构建并检查向量索引 |
| `BM25Builder` | 构建并检查关键词倒排索引 |
| `QualityGate` | 汇总元数据和两个索引状态，决定是否进入测试与发布 |
| `PoCTestSuite` | 运行检索、引用、冲突和无依据处理测试 |
| `MaintenanceReport` | 输出成功、失败、待 OCR 和待联网复核清单 |

### 4.3 消息顺序

| 编号 | 发送方 → 接收方 | 消息与数据 | 约束 |
|---|---|---|---|
| 1 | Maintainer → IngestionEntry | `addOfficialDocument(file, metadata)` | 只接收公开官方资料 |
| 2 | IngestionEntry → MetadataGate | `validate(source, type, size, hash)` | 来源或日期缺失时不进入正式索引 |
| 3 | MetadataGate → ParserOCR | `parse(documentRef)` | 保留原件，不覆盖旧版本 |
| 4 | ParserOCR → LocalKnowledge | `saveOriginal + extractedText + locator` | 正文提取不等于向量化 |
| 5 | LocalKnowledge → IndexCSV | `upsertMetadata(record)` | 更新当前 CSV 元数据；方向是知识资产到索引 |
| 6 | LocalKnowledge → ChunkBuilder | `buildChunks(text, headings)` | 保留页码或段落定位 |
| 7a | ChunkBuilder → ChromaBuilder | `embedAndUpsert(chunks)` | 使用固定分块规则和嵌入模型 |
| 7b | ChunkBuilder → BM25Builder | `tokenizeAndUpsert(chunks)` | 保留规则名称、文号和年度 |
| 8a | ChromaBuilder → QualityGate | `indexStatus + counts` | 返回向量索引构建状态 |
| 8b | BM25Builder → QualityGate | `indexStatus + counts` | 返回关键词索引构建状态 |
| 8c | IndexCSV → QualityGate | `metadataStatus` | 返回元数据索引状态 |
| 9 | QualityGate → PoCTestSuite | `runTests` | 仅当 Chroma 与 BM25 均为 `PASS` 才进入 |
| 9.1 | PoCTestSuite → QualityGate | `testResult` | 测试失败不得进入发布 |
| 10 | QualityGate → MaintenanceReport | `publishAllowed` | 双索引与测试均通过后才允许发布 |
| 10.1 | MaintenanceReport → IngestionEntry | `statusFeedback` | 回传成功、失败与待核项，不反向覆盖资料 |

### 4.4 发布闸门

```text
ChromaBuilder ─ status ─┐
BM25Builder ── status ─├─ QualityGate ─ 两项 PASS ─ PoCTestSuite ─ 测试通过
IndexCSV ───── status ─┘                  │
                                           └─ 任一项失败：不发布
```

只有两个检索索引均通过构建检查，质量闸门才允许进入离线测试。测试通过后才生成发布许可。失败时保留上一版可用索引，并在更新报告中记录待修复项。

## 5. 术语与响应字段

| 术语/字段 | 定义 |
|---|---|
| MVP | Minimum Viable Product，首版最小可用产品 |
| API | Application Programming Interface，应用编程接口 |
| RAG | Retrieval-Augmented Generation，检索增强生成 |
| BM25 | 结合词频、逆文档频率和文档长度的关键词排序算法 |
| RRF | Reciprocal Rank Fusion，倒数排名融合 |
| OCR | Optical Character Recognition，光学字符识别 |
| CSV | Comma-Separated Values，逗号分隔值文件 |
| `requestId` | 请求追踪标识 |
| `answerStatus` | 回答状态，见 3.5 |
| `citations` | 支撑结论的官方证据列表 |
| `documentId` | 知识库资料记录编号 |
| `sourceUrl` | 官方原文网址 |
| `sourcePath` | 官方原文或整理稿在仓库中的路径 |
| `publishedAt` | 资料发布日期，格式 `YYYY-MM-DD` |
| `verifiedAt` | 最近核验日期，格式 `YYYY-MM-DD` |
| `applicableGrade` | 适用年级 |
| `applicableMajor` | 适用专业 |
| `policyStatus` | `current` 当前有效、`current_reference` 当前参考、`semester_valid` 学期有效、`annual_notice` 年度通知、`process_reference` 截止后流程参考、`historical` 历史参考、`repealed` 已废止、`pending_verification` 待核验 |
| `locator` | 原文章节、页码或段落定位 |
| `limitations` | 回答的时效、证据或适用性限制 |

引用链接应优先指向官方原文；原始链接不可用时可指向仓库中的原始资料副本，并明确说明。`policyStatus` 不能由模型随意推断，应来自知识库元数据。

## 6. 异常与降级

| 场景 | 处理 |
|---|---|
| 问题缺少必要信息 | 按 4a—4d 返回追问；用户补充后按 5/5.1 重提 |
| Chroma 不可用 | 使用 BM25 结果并标记降级 |
| BM25 不可用 | 使用语义结果，但提示精确匹配能力下降 |
| 两路结果冲突 | RRF 后核验版本与适用范围；仍冲突时返回 `conflict` |
| Qwen 返回无来源结论 | 删除无引用结论；无法校正时返回证据不足 |
| Qwen 或 Tavily 超时 | 返回可读检索摘要，标记 `degraded` |
| Tavily 结果不是官方来源 | 只作为线索，不作为最终政策依据 |
| CSV 与知识库基准不一致 | 记录差异，交由知识库负责人核对，不擅自删减资料 |
| Chroma 或 BM25 构建失败 | QualityGate 阻止测试和发布，保留上一可用索引 |

## 7. 数据库范围协同

本文件将数据库视为**待与数据库负责人确认的概要设计范围**。当前技术架构没有把独立数据库列为 v1.0 默认部署组件，但数据库设计成果仍可用于后续历史会话、元数据管理、审计或运营需求。

在赵紫龙与丁晓炜、王智洋确认前，文档不使用以下结论：

- “v1.0 已经部署数据库”；
- “数据库不属于项目设计”；
- “当前 JSON/CSV 方案可以替代数据库设计成果”。

确认后应在技术架构和数据库说明书中同步写明首版是否部署、存储边界和迁移条件。
