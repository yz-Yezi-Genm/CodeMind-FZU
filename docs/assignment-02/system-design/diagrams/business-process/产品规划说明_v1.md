# CodeMind-FZU 产品规划说明

**版本**：v1.4
**日期**：2026-11-08

---

## 一、产品定位

CodeMind-FZU 是面向福州大学计算机与大数据学院（软件学院）本科生的校园事务与发展信息智能助手。它不替代学校、学院的官方发布渠道，而是把分散在不同官网、通知和附件中的资料集中整理，通过领域知识库和 Agent 任务流程，让学生用一次自然语言提问就能查到有来源、可核对的答案。

通用大模型可以回答常识性问题，但回答具体年份的奖学金条件、竞赛认定类别或推免政策时容易脱离依据。本产品的核心价值在于：**回答必须能追溯到官方资料，证据不足时明确说明，而不是给出一个看似确定的答案。**

## 二、目标用户

主要用户为学院本科生，重点服务大一至大三学生：

- **大一学生**：关注学籍、选课、考试、转专业等基础事务；
- **大二学生**：开始接触竞赛、创新学分、奖学金和辅修；
- **大三学生**：重点关注推免、升学、科研实践和实验室机会。

问卷样本中大二、大三学生合计占 90.48%，因此首版优先支持的业务方向主要围绕这两个年级的高频问题设计，同时保留对大一事务的覆盖。

## 三、需求依据

2026 年 10 月面向计算机相关专业学生发放问卷，回收有效样本 84 份。以下结论只代表本次小样本探索性调查，不外推为全体学生意见。

| 调研发现 | 数据 | 对产品的直接影响 |
|---|---|---|
| 信息分散，不知道从哪里找 | 64/84（76.19%） | 建立统一查询入口，优先整合官方来源资料 |
| 担心信息不准确 | 64/84（76.19%） | 回答展示来源、版本和适用范围，证据不足时拒答 |
| 缺少针对年级和专业的建议 | 52/84（61.90%） | 必要时追问年级、专业、用途，再组织回答 |
| 缺少过来人经验参考 | 52/84（61.90%） | 经验类材料首版暂不纳入，先评估审核机制 |
| 升学与就业发展重要程度最高 | 4.43/5；保研/升学规划单选占 42.9% | 推免与升学政策查询作为优先验证方向 |
| 学院资源导航重要程度 4.38/5 | 单选优先项占 19.1% | 培养方案与办事渠道查询作为重要方向 |

## 四、整体功能规划

产品采用 Web 软件形式，**整体规划**五大业务方向，覆盖学生从入学到升学的完整事务面。自然语言问答、任务识别、知识检索、来源展示、证据核验和必要追问属于支撑这五大方向的**共用技术能力**，不单独算作业务模块。

以下口径与团队博客 2.4.2《核心功能规划》一致：

| 功能方向 | 功能说明 | 计划范围 |
|---|---|---|
| 政策与事务办理 | 查询奖学金、评优评奖及其他校园事务的申请条件、材料要求、办理流程和注意事项 | v1.0 优先支持有官方资料依据的查询 |
| 升学与就业发展 | 查询推免、升学及相关发展政策，整理阶段性准备事项 | v1.0 优先支持官方政策查询；个性化规划逐步迭代 |
| 学院资源导航 | 查询培养方案、学院资源、办事渠道及本科生可用的学习科研资源 | v1.0 优先支持资料查询与导航 |
| 竞赛与科研信息 | 查询竞赛认定规则、科研实践资料及相关机会信息 | v1.0 优先支持已有官方资料的查询；动态机会筛选后续完善 |
| 个人成长档案与长期规划 | 在用户主动提供信息的基础上，整理阶段目标、成长经历并辅助制定后续计划 | 后续迭代方向，不作为 v1.0 的必要交付 |

**整体规划与首版范围的区别**：

| 层次 | 包含方向 | 说明 |
|---|---|---|
| 整体规划 | 五大方向 | 覆盖学生从入学到升学的完整事务面，是系统的长期业务范围 |
| 首版（v1.0）优先支持 | 前四大方向 | 政策与事务办理、升学与就业发展、学院资源导航、竞赛与科研信息，只做有官方资料依据的查询与导航 |
| 后续迭代 | 第五方向 | 个人成长档案与长期规划，不纳入首版交付 |

## 五、首版（v1.0）交付范围

整体规划不等于首版交付。v1.0 只做有官方资料依据的查询，业务范围就是第四节中的**前四大方向**。

下面列出的三个任务是**代表性测试任务**，仅用于验证 Agent 的共用流程（检索、证据核验、回答组织、来源展示这条闭环）能否跑通。它们是验证手段，不定义系统的业务范围，也不意味着业务范围只有这三项；系统的业务范围以第四节五大方向为准。

1. **竞赛认定类别及证明材料查询**——竞赛在学院的认定类别、所需证明材料及适用规则（对应竞赛与科研信息方向）；
2. **奖学金申请条件与流程查询**——各级奖学金的申请条件、材料要求和办理流程（对应政策与事务办理方向）；
3. **保研基本条件查询**——推免的基本资格、成绩与附加条件要求（对应升学与就业发展方向）。

### 5.1 各方向资料支撑现状

业务方向的规划需要与实际知识库覆盖对应，避免规划超出资料能力。

| 业务方向 | 现有资料支撑 | 首版能支持的查询 | 待补充核验 |
|---|---|---|---|
| 政策与事务办理 | 学生管理规定、奖学金评定办法、院级奖学金及专项奖教奖学金通知 | 奖学金条件、材料与流程，以及学籍、学生证等基础事务 | 部分通知时效仍待联网复核 |
| 升学与就业发展 | 学院推免复试方案及实施细则 | 推免资格、成绩与附加条件 | 就业相关资料尚少，个性化规划不纳入首版 |
| 学院资源导航 | 学位工作细则、培养方案、选课与辅修办法、进实验室通知、开放探索性实验项目通知 | 培养方案与学位要求、办事渠道、课程与辅修、本科生可申报的学习科研项目 | 学院资源类条目分散，部分仅完成本地登记，适用范围与时效待逐条核验 |
| 竞赛与科研信息 | 竞赛报名通知、创新学分认定办法、课程替代与学分认定办法 | 竞赛认定类别、证明材料与创新学分 | 动态机会信息暂不支持自动筛选 |
| 个人成长档案与长期规划 | 无对应资料 | 首版不交付 | 需先明确数据保存与用户控制方式 |

**学院资源导航方向**：当前已有培养方案、学位细则、选课辅修、进实验室和开放实验项目等官方资料，可以支持培养方案与学位要求查询、办事渠道导航、本科生学习科研项目查询；但资料条目比较分散，部分只完成本地登记，适用范围和时效还在逐条核验，核验完成前不把相关查询写成已完全实现的能力。

### 5.2 共用查询闭环

各方向的代表性任务共用同一条查询闭环：

```
学生提出问题 → 信息不足时追问 → 检索领域知识库 → 证据核验
        → 证据充分：组织回答并展示来源
        → 证据不足/版本冲突/时效未确认：如实提示，不编造结论
```

**首版不交付**：完整的个性化升学规划、个人成长档案、动态机会自动推送、经验帖类 UGC 内容，以及 ESP32 硬件联动。整体规划中的"个人成长档案与长期规划"方向在首版没有对应交付物。

## 六、开发路线

各阶段以明确产出和验收标准作为进入下一阶段的门槛。为避免把规划当成已完成能力，功能状态按三类区分：**计划功能**（已规划、尚未实现）、**已实现功能**（当前可运行或已完成的部分）、**待验证功能**（已搭建但需真实资料和测试确认的部分）。

当前实际状态：已完成 Figma 交互原型、44 条资料登记与部分核验、离线 PoC（9 项自动化测试通过，使用虚构样例）；真实模型问答、检索接入、前后端集成与部署均属于计划或待验证功能。

| 阶段 | 主要工作 | 阶段产出 | 验收标准 |
|---|---|---|---|
| 一：完善领域资料 | 完成待 OCR 文件，逐条核验来源、日期、适用范围与时效 | 资料清单、正文文本、核验状态记录 | 44 条资料全部有登记与状态标记；未核实资料明确标注，不与已确认资料混用 |
| 二：接入检索与 Agent | 确定检索方案，用真实资料测试，集成模型 API 与追问 | 可运行的检索与 Agent 流程 | 首版代表性查询任务能完成"理解—检索—回答"，展示来源或说明证据不足 |
| 三：前后端集成 | 前端与 FastAPI 后端联调，覆盖输入校验与异常分支 | 可联调的 Web 应用 | 前端可发起查询并收到结构清楚的回答或失败提示；模型不可用、检索失败均有明确提示 |
| 四：测试与改进 | 按固定用例检查事实正确性、来源、适用范围与拒答 | 测试记录、问题清单与修复记录 | TC-01~TC-07 逐条执行并记录结果，未通过用例如实标记、闭环修复 |
| 五：部署与验收 | 完成部署、使用说明与验收材料 | 可访问的部署地址与验收材料 | 部署地址可实际访问，前四个业务方向的代表性查询在线验证通过，测试记录与实际版本一致 |

各阶段只在验收标准达成后才进入下一阶段；规划中的功能在实际完成并验证前，不写成已实现能力。

## 七、关键设计原则

1. **官方来源优先**：资料只收录学校、学院官方渠道，记录发布部门、日期、链接和核验状态；联网核验仅采信官方公开来源，不直接采用普通搜索结果；
2. **版本可追溯**：同一事项的不同版本分别保存，过期资料标记为历史参考，不直接删除；
3. **不确定性显性化**：资料不足、冲突或时效无法确认时，提示限制并建议线下核实；
4. **信息最小化**：只收集完成当前任务所必需的信息，年级、专业、目标等由用户在必要时主动提供；
5. **不提前宣称效果**：领域定制是否优于通用模型，以真实资料接入后的对照实验数据为准。
