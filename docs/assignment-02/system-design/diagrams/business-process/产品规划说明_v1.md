# CodeMind-FZU 产品规划说明

**版本**：v1.2
**日期**：2026-11-08

---

## 一、产品定位

CodeMind-FZU 是面向福州大学计算机与大数据学院（软件学院）本科生的校园事务与发展信息智能助手。它不替代学校、学院的官方发布渠道，而是把分散在不同官网、通知和附件中的资料集中整理，通过领域知识库和 Agent 任务流程，让学生用一次自然语言提问就能查到有来源、可核对的答案。

通用大模型可以回答常识性问题，但回答具体年份的奖学金条件、竞赛认定类别或推免政策时容易脱离依据。本产品的核心价值在于：**回答必须能追溯到官方资料，证据不足时明确说明，而不是给出一个看似确定的答案。**

## 二、目标用户

主要用户为学院本科生，重点服务大一至大三学生：

- **大一学生**：关注学籍、选课、考试、转专业等基础事务；
- **大二学生**：开始接触竞赛、创新学分、奖学金和辅修；
- **大三学生**：重点关注推免、升学、科研实践和实验室机会。

问卷样本中大二、大三学生合计占 90.48%，因此首版场景优先围绕这两个年级的高频问题设计，同时保留对大一事务的覆盖。

## 三、需求依据

2026 年 10 月面向计算机相关专业学生发放问卷，回收有效样本 84 份。以下结论只代表本次小样本探索性调查，不外推为全体学生意见。

| 调研发现 | 数据 | 对产品的直接影响 |
|---|---|---|
| 信息分散，不知道从哪里找 | 64/84（76.19%） | 建立统一查询入口，优先整合官方来源资料 |
| 担心信息不准确 | 64/84（76.19%） | 回答展示来源、版本和适用范围，证据不足时拒答 |
| 缺少针对年级和专业的建议 | 52/84（61.90%） | 必要时追问年级、专业、用途，再组织回答 |
| 缺少过来人经验参考 | 52/84（61.90%） | 经验类材料首版暂不纳入，先评估审核机制 |
| 升学与就业发展重要程度最高 | 4.43/5；保研/升学规划单选占 42.9% | 推免与升学政策查询作为优先验证方向 |
| 学院资源导航重要程度 4.38/5 | 单选优先项占 19.1% | 培养方案与办事渠道查询作为重要方向 |

## 四、整体功能规划

产品采用 Web 软件形式，**整体规划**五大业务方向，覆盖学生从入学到升学的完整事务面。自然语言问答、任务识别、知识检索、来源展示、证据核验和必要追问属于支撑这五大方向的**共用技术能力**，不单独算作业务模块。

| 功能方向（整体规划） | 说明 |
|---|---|
| 政策与事务办理 | 奖学金、评优评奖等事务的条件、材料与流程 |
| 升学与就业发展 | 推免、升学、交换出国政策及阶段性准备事项 |
| 学院资源导航 | 培养方案、办事渠道、学习科研资源 |
| 竞赛与科研信息 | 竞赛认定规则、科研实践资料与机会 |
| 个人成长档案与长期规划 | 基于用户主动提供的信息整理目标与经历 |

## 五、首版（v1.0）交付范围

整体规划不等于首版交付。v1.0 只做有官方资料依据的查询，**四个核心场景**：

1. **竞赛认定类别及证明材料查询**——竞赛在学院的认定类别、所需证明材料及适用规则；
2. **奖学金申请条件与流程查询**——各级奖学金的申请条件、材料要求和办理流程；
3. **保研基本条件查询**——推免的基本资格、成绩与附加条件要求；
4. **交换与出国相关信息查询**——校际交换、出国交流项目的申请条件与相关政策。

### 5.1 资料支撑现状

四个场景的规划与实际知识库覆盖需要对应，避免规划超出资料能力。对照当前知识库索引：

| 核心场景 | 现有资料支撑 | 交付判断 |
|---|---|---|
| 竞赛认定类别及证明材料 | 有竞赛报名通知、创新学分认定办法、课程替代与学分认定办法 | 可按现有官方资料交付 |
| 奖学金申请条件与流程 | 有本科奖学金评定办法、院级奖学金通知、专项奖教奖学金通知 | 可按现有官方资料交付 |
| 保研基本条件 | 有学院推免复试方案及实施细则 | 可按现有官方资料交付 |
| 交换与出国相关信息 | **当前索引中没有交换、出国、交流项目的专题资料**，仅见托福雅思成绩替代课程等间接内容 | **资料缺口，暂不具备完整交付条件** |

**交换与出国场景的能力限制**：在官方资料（项目要求、申请条件、办理流程）补齐之前，该场景不按完整查询能力交付。系统遇到相关问题时如实说明资料尚未收录、建议向国际合作与交流主管部门核实，不编造项目信息；待知识库负责人补充对应官方资料并完成核验后，再正式开放该场景。

四个场景共用同一条查询闭环：

```
学生提出问题 → 信息不足时追问 → 检索领域知识库 → 证据核验
        → 证据充分：组织回答并展示来源
        → 证据不足/版本冲突/时效未确认：如实提示，不编造结论
```

**首版不交付**：完整的个性化升学规划、个人成长档案、动态机会自动推送、经验帖类 UGC 内容，以及 ESP32 硬件联动。整体规划中的"个人成长档案与长期规划"方向在首版没有对应交付物。

## 六、开发路线

各阶段以明确产出和验收标准作为进入下一阶段的门槛。

| 阶段 | 主要工作 | 阶段产出 | 验收标准 |
|---|---|---|---|
| 一：完善领域资料 | 完成待 OCR 文件，逐条核验来源、日期、适用范围与时效 | 资料清单、正文文本、核验状态记录 | 44 条资料全部有登记与状态标记；未核实资料明确标注，不与已确认资料混用 |
| 二：接入检索与 Agent | 确定检索方案，用真实资料测试，集成模型 API 与追问 | 可运行的检索与 Agent 流程 | 四个核心场景的代表性问题能完成"理解—检索—回答"，展示来源或说明证据不足 |
| 三：前后端集成 | 前端与 FastAPI 后端联调，覆盖输入校验与异常分支 | 可联调的 Web 应用 | 前端可发起查询并收到结构清楚的回答或失败提示；模型不可用、检索失败均有明确提示 |
| 四：测试与改进 | 按固定用例检查事实正确性、来源、适用范围与拒答 | 测试记录、问题清单与修复记录 | TC-01~TC-07 逐条执行并记录结果，未通过用例如实标记、闭环修复 |
| 五：部署与验收 | 完成部署、使用说明与验收材料 | 可访问的部署地址与验收材料 | 部署地址可实际访问，四个核心场景在线验证通过，测试记录与实际版本一致 |

## 七、关键设计原则

1. **官方来源优先**：资料只收录学校、学院官方渠道，记录发布部门、日期、链接和核验状态；联网核验仅采信官方公开来源，不直接采用普通搜索结果；
2. **版本可追溯**：同一事项的不同版本分别保存，过期资料标记为历史参考，不直接删除；
3. **不确定性显性化**：资料不足、冲突或时效无法确认时，提示限制并建议线下核实；
4. **信息最小化**：只收集完成当前任务所必需的信息，年级、专业、目标等由用户在必要时主动提供；
5. **不提前宣称效果**：领域定制是否优于通用模型，以真实资料接入后的对照实验数据为准。
