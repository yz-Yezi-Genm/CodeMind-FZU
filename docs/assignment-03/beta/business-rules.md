# Beta 业务规则：追问与证据不足判定

面向福州大学计算机与大数据学院（软件学院）本科生的校园事务信息 Agent。本文件在 Alpha 规则基础上定义四个场景在学生提问时的判定规则：哪些问题可以直接回答、哪些必须先追问、哪些只能返回证据不足，以及每种情况的预期回答形态。

基线为 Beta 阶段最新 `main`，遵循已合并的 Alpha 接口契约（`AnswerStatus`、`AnswerMode`）与《Beta 接口规范 V2.1-Final》。本文件不新增状态值，不修改公共字段，规则通过既有 `clarification_rule` / `evidence_check` 注入点落地。

四个场景：

| 编号 | 场景 | 对应业务方向 |
| --- | --- | --- |
| S1 | 竞赛认定（含创新学分与综测加分） | 竞赛与科研信息 |
| S2 | 奖学金申请 | 政策与事务办理 |
| S3 | 推免条件咨询 | 升学与就业发展 |
| S4 | 学院资源导航（Beta 新增） | 学院资源导航 |

## 1. 硬约束

1. **只答知识库原文**。回答内容必须是已入库资料中可逐字核对的条件、分值、材料、流程。不补充知识库之外的院校要求，不推算未公布的分值或比例。
2. **不推断个人资格**。学生问"我能不能"，Agent 给的是政策条件清单和自查方法，不是"你能/不能"的判定。个人适用性核验尚未接入。
3. **三个口径不能混用**。创新学分原始分、综测加分、推免评价是三套独立规则：原始分不等于学分，也不等于综测加分；创新学分办法不能替代综测办法。同一份获奖材料在三处的算法不同，回答时必须声明当前用的是哪一套。
4. **追问只补用户信息**。资料缺失不能用追问掩盖；缺资料就直接返回证据不足。
5. **一次只问一个**。每轮追问只解决一个必要项，不列清单式连环问。

## 2. 判定总则

### 2.1 状态与回答方式

沿用契约枚举，不扩展：

| 条件 | status | answer_mode | answer |
| --- | --- | --- | --- |
| 信息齐备且有可用证据 | `answered` | `current_policy` | 有内容 |
| 信息齐备，依据为办理流程、材料清单、年度通知 | `answered` | `procedure_reference` | 有内容 |
| 信息齐备，依据为已废止办法或已过期的年度通知 | `answered` | `historical` | 有内容，并注明失效或过期 |
| 缺用户侧必要信息 | `needs_clarification` | null | null，`clarifying_question` 有值 |
| 资料缺失、版本冲突、无法确认是否为现行版本 | `insufficient_evidence` | `insufficient_data` | 有内容（说明缺什么） |

时效与证据不足的分界：资料本身有效、只是对应年度的办理周期已经结束，不属于证据不足，按 2.5 正常回答并标 `historical`；只有资料拿不到、新旧版本冲突或无法判断是否现行时才判 `insufficient_evidence`。

`citations` 只放本轮实际采用的片段。证据不足时 `citations` 留空，不摆出无关资料充数。

### 2.2 判定顺序

按以下顺序判，命中即停：

1. **主题不明**（如"怎么办""这个怎么弄"）→ 追问具体事项。
2. **主题明确但资料缺失、版本冲突或无法确认现行性** → 证据不足，不追问。追问解决不了资料问题。
3. **主题明确、资料有效但年度办理周期已结束** → 不判证据不足，按 2.5 正常回答并标 `historical`，说明该年度已结束、新年度需查新通知。
4. **主题明确、资料可用，但缺适用性必要信息**（学年、年级、奖学金类别、竞赛级别等）→ 追问。
5. **齐备** → 回答，并按 2.1 选 `answer_mode`。

### 2.3 追问顺序

固定为 **事项 → 学年/学期 → 年级 → 场景细节项**（级别、获奖等级、个人/集体、前八名成员、完成人排序、报考专业）。每轮只输出一个 `clarifying_question`。

- "2024级"是入学年级，不是"2024学年"，两者不能互相替换。
- 学生已在同一会话补充过的信息不重复追问；但当前 HTTP 入口不保存会话状态，联调时以完整问题重发为准。
- 追问句给出可选项，不问开放式长问题。例："你想问的是创新学分认定，还是综测加分？"
- 年度不是默认追问项。现行通用政策与库内唯一一种年度通知都不问年度，按 2.5 处理。

### 2.4 分事项独立判断

一个问题含多个事项时（如"这个奖对创新学分和综测分别有什么用"），逐项判断，不因为其中一项缺依据就拒答全部：

- 有依据的事项：正常回答并给出可核对来源。
- 无依据的事项：明确写"这部分目前无法确认"，并说明缺哪份资料。
- 整体 `status` 为 `answered`，`warnings` 记录缺依据的事项代码。
- S4 多类别问题同样逐类判断，例如"实验室和培养方案都讲讲""学院通知在哪看，实验室怎么报名"。一个类别缺资料只影响该类，不能让另一类已命中的证据一起被拒；回答按类别分段说明。

### 2.5 时效、版本与年度规则

- 同一事项有新旧两版时，只采用现行版，旧版转 `historical` 并提示已被替代。奖学金 2024 版已废止，一律让位于 2026 版；综测 2021 版已废止，让位于 2026 版。
- 年度通知按办理周期判定：处于对应周期内按 `procedure_reference`；周期已结束（报名、材料提交、评审或公示节点已过）转 `historical`，并提示需查新一年度通知，不把当年条件套到未来年度。
- 年度追问统一按三条执行，避免所有问题都先问学年：
  1. 现行通用政策（校级奖学金办法、综测办法、创新学分办法）不问年度，直接按现行版作答。
  2. 库内只有单一年度通知时（院级 2026、星火 2026、蓝桥杯 2026、推免 2027）不追问年度，直接用该年度作答，并在答案开头声明年度与办理状态。
  3. 库内存在多个年度且结论可能不同时才追问年度；询问库外未来年度直接证据不足，不追问。
- 资料状态为"仅作参考"或"具体项目以认定目录和学院审核为准"的，回答时必须原样带上这句限定。

Beta 阶段新增两条硬规则：

1. 历史资料不等于无效资料，但历史资料不能作为现行政策或当前办理依据。问"现在/今年/最新"时，`historical`、`expired`、`superseded` 片段一律不进入回答；问"去年/当时/旧办法"或明确写出历史年度时才允许，且资料适用年度必须与问题年度对应。未指定年度的旧政策不进入回答，避免把某一年的条件套到现行口径。
2. `policy_status` 写明"无法确认是否为现行版本"或时效核验为 `pending` / `uncertain` 时，直接拒绝该片段，不做推测性使用。

历史政策按资料情况分档处理：

| 资料情况 | 业务处理 | 允许的 `answer_mode` |
| --- | --- | --- |
| 当前有效的通用政策 | 可支持现行政策回答 | `current_policy` |
| 当前正在办理的年度通知 | 可支持办理流程参考 | `procedure_reference` |
| 已结束的年度通知 | 可回答该年度历史情况，须标注年度 | `historical` |
| 已被新版本替代的旧政策 | 可回答历史问题，须说明已被替代 | `historical` |
| 无法确认是否为现行版本 | 不作为现行政策依据 | `insufficient_data` |
| 来源未核验、未通过人工审核、`retrieval_status` 非 `enabled` | 拒绝使用 | 不适用 |

年度判断仍以元数据中的适用年度为准，不把发布日期当作适用年度。用户未说明年度而年度会影响结论时，按 2.3 追问；库外未来年度直接证据不足。

### 2.6 多轮对话的时间口径

多轮对话里，时间判断以本轮问题写明的口径为准，历史消息只补本轮没写的槽位。本轮只要出现明确年份、今年/去年/前年、现在/目前/当前，或“当时/以前”等历史表达，就只用本轮文本判断年度、时效与名额，不把前几轮拼进来。

典型处理：第一轮问 2025 年、第二轮问 2024 年时，不能因为历史里还有 2025 就让 2025 年资料通过；第一轮问“2026 年当时招几个”、第二轮问“现在还剩几个名额”时，历史里的“当时”不能让当前名额检查失效。反过来，本轮问历史人数，也不应被上一轮的“现在”拦住。只有当本轮完全没写时间时，才继承最近一条带时间表达的 user 消息。

### 4.2 必要条件

回答创新学分：赛事名称、获奖级别（国际级、国家级、省部级、校级）、获奖等级或排名、个人或集体项目、作品名称、本人是否在前八名内（集体项目）。

回答综测加分：赛事名称、获奖等级（最高等级奖、次高等级奖、第三等级奖）、个人或集体、本人完成人排序（团队项目按排序系数计算）、成果取得学期与第一署名单位。

回答推免相关性：仅有方向性提示，不作为作答条件。

### 4.3 追问条件

| 缺失项 | 追问示例 |
| --- | --- |
| 用途 | "你想了解的是创新学分认定、综测加分，还是推免相关？" |
| 赛事名称 | "请说一下竞赛全称，例如全国大学生数学建模竞赛。" |
| 获奖级别 | "这个奖是国家级、省部级还是校级？" |
| 获奖等级 | "获得的是特等奖、一等奖、二等奖还是三等奖？" |
| 个人或集体 | "这是个人参赛还是团队作品？" |
| 前八名成员 | "团队作品里你排第几？创新学分只认定排名前八名成员。" |
| 完成人排序 | "你在完成人里排第几？综测团体项目按排序系数计算。" |

### 4.4 证据不足条件

| 情形 | 处理 |
| --- | --- |
| 询问某赛事是否属于教务处认定范围或属于哪一级别 | 证据不足：认定目录未入库 |
| 询问某赛事的综测具体加分值（如蓝桥杯省赛二等奖） | 证据不足：可说明现有分档规则，但缺《学科竞赛等级目录》，无法确定赛事类别与具体分值，整体返回 `insufficient_evidence` / `insufficient_data` |
| 询问竞赛在推免中如何计分 | 证据不足：校内推免资格推荐办法未入库 |
| 询问本年度申报窗口或截止时间 | 证据不足：仅有"每学年受理一次"的原则，无当期通知 |

### 4.5 预期回答方式

结构固定为四段：结论（能认定什么、按哪张表）→ 计算依据（级别、等级、个人/集体对应的原始分）→ 限定（认定目录与学院审核待核验）→ 来源。附 `citations`，`answer_mode` 为 `current_policy`。

可稳定作答的内容：

- 认定范围：校级及以上各类竞赛、科研训练与创新创业训练项目、公开发表作品与成果、个性素质拓展。
- 竞赛原始分：国际级 6/5/4/3（个人）、5/4/3/2（集体）；国家级 5/4/3/2、4/3/2/1.5；省部级 4/3/2/1.5、3/2/1.5/1；校级 2/1.5/1、1.5/1/0.5，按特等奖、一等奖、二等奖及单项奖、三等奖顺序。
- 计分规则：不同竞赛可累加；同一竞赛同一作品同年度不同级别奖项只取最高一项；同一竞赛不同赛道可累加，同赛道不同作品同年度只取最高；未计分的获奖只记录、原始分记 0。
- 成员限制：仅认定排名前八名成员；高水平运动员体育类竞赛获奖不予认定。
- 学分与成绩：记 2 学分，原始分累计 8/6/4/2 分别记优秀、良好、中等、合格，低于 2 分不予记载；纳入课程绩点。
- 申报规则：原则上每学年受理一次，在校期间只可申请一次，成绩入档后不得撤销或更改；提交原始分认定申请及证明材料扫描件，由学院审核、分管教学领导审批。

综测竞赛加分的计算条件（逐条核对，缺一项不出具体分值）：

- 学期与署名：成果须为上一学期内取得，且以福州大学为第一署名单位；有证书以证书日期为准，无证书以竞赛日期为准。
- 证明材料：须提供获奖证书或成果鉴定证书；无证书可提供公示页面网址或组织单位证明信；无法证明的暂不承认。
- 署名顺位：一项成果由多人共同完成的，署名第一按相应级别等次加分，其余成员降一等级加分。
- 名次折算：评奖不分等级时按次高等级奖计；以名次计的第 1 名按最高等级奖、第 2—3 名按次高等级奖、第 4—8 名按第三等级奖。
- 同类去重：同类不同级别赛事获多个奖项，按最高奖项加分，此前已计入的分值予以扣减，不累计。
- 团队排序系数：团体项目按"等级得分 × 排序系数"计算，按完成人排序依次为 1.0、0.8、0.6、0.4、0.2，其他队员 0.1；不区分排名的赛事取平均值。体育竞赛经认定的主力队员加分、其他队员减半；文化艺术比赛经认定的主要演员加分、其他演员减半。
- 叠加待确认：同一团体项目同时涉及"非第一署名降一等级"与"排序系数"时，两条附则如何叠加办法未写明，须学院细则确认。未确认前只给单项计算，不给合并后的最终分值。

系数演示（仅演示排序系数，不是最终得分）：校级竞赛最高等级奖、第二完成人按 2 × 0.8 = 1.6 换算；同一项目为第一完成人则按 2 × 1.0 = 2 换算。此处只体现排序系数的作用，署名顺位降档与排序系数的叠加方式尚未确认，不得把 1.6 或 2 作为最终加分对外给出。

### 5.5 预期回答方式

结构：类别归属 → 参评基本条件 → 该层级的具体门槛（排名、金额、比例或材料）→ 时间与组织方式 → 来源。

可稳定作答的内容：

- 三类奖学金划分，以及校级含优秀学生综合奖学金、文化科技创新创业奖学金、单项奖学金。
- 参评基本条件：遵守宪法法律与校纪校规、道德品质良好、恪守学术诚信、学习勤奋成绩优良、积极参加社会工作与文体活动、身心健康。
- 不具备资格三种情形：评定学期受警告以上处分且在处分期限内；休学或保留学籍；除任意选修课外有课程不及格。
- 优秀学生综合奖学金：一等奖 1500 元/学期、学期综测专业排名前 10%；二等奖 1000 元、前 20%；三等奖 500 元、前 40%。评定比例上限：校级实验班 36%（一等 6%、一二等合计 16%）；非校级实验班 18%（一等 3%、一二等合计 8%）。大四下学期无专业课程或学期总学分低于 15 学分的，不评综合奖学金，改评专技奖，每人不超过 300 元。
- 单项奖学金：学习进步奖为评定学期进步名次超过 30 名或大于 40%，每人每学期不超过 400 元；精神文明建设奖每人每学期不超过 300 元；获奖比例不超过学生总数 25%。
- 评定周期：每学期一次，每年 4 月、10 月；学院组织申请、评审、公示并处理异议。

## 7. S4 学院资源导航

S4 只回答学院公开资源"有什么、在哪、适用谁、怎么走官方流程"，不判定个人是否被实验室录取，不提供导师评价，不承诺实时名额。

### 7.1 资源类别与边界

S4 内部按六类判断，并要求资料的 `category_name` 使用同名正式名称；规则只按该字段定类，不再用正文关键词兜底。

| 标签 | `category_name` | 覆盖内容 | 用户意图 |
| --- | --- | --- | --- |
| R1 | 通知与办事渠道 | 通知公告、一般办理流程与材料、办事入口 | 在哪看、要交什么、找哪个部门 |
| R2 | 培养方案与课程 | 培养方案、选课、辅修、学分认定口径、学位要求 | 学什么、修多少、怎么选 |
| R3 | 实验室与科研团队 | 实验室名称、地点、联系人、电话邮箱、接收人数、接收条件、考核方式、报名截止、报名材料、提交邮箱、选拔流程 | 谁、在哪、谁能进、怎么进、找谁 |
| R4 | 研究方向与公开介绍 | 实验室名称、简介、研究方向、科研成果、学生典型事迹、教师主页 | 研究什么、有什么成果、去哪看介绍 |
| R5 | 科研实践与竞赛 | 本科生科研项目、竞赛报名与目录、创新学分与奖励入口 | 课堂外可参与什么、去哪报名 |
| R6 | 学院公开信息与联系方式 | 学院与系所简介、办公地点、电话邮箱、官网入口 | 学院怎么联系、在哪办公 |

边界口径：

- R1 有时效与办理窗口；R6 是长期公开信息。同一 URL 只归一类。
- 实验室层面的联系人归 R3，不归 R6；R6 只回答学院层面的公开联系方式。
- 青禾计划 24 条实验室记录每条同时含 R3、R4 信息，拆成两个规范化片段，共 48 个片段，并分别使用独立的 `DocumentMetadata` 分类记录；不能把整条记录强行归为单一类别。R3 包 `record_code` 为 `计算机学院-2026-青禾计划-R3`，R4 包为 `计算机学院-2026-青禾计划-R4`，`version_no` 均为 `import-1`，避免 `(record_code, version_no)` 查重报错；两包各登记一份按列裁剪的派生 CSV，原始 XLSX 只在来源说明中记录一次。
- R3 片段正文首行标 `[R3 招募条件]`，R4 片段正文首行标 `[R4 研究方向]`，让 BM25 先按类别区分同源内容，再交给证据判断；R3 保留实验室名称、地点、联系人、电话/邮箱、接收人数、接收条件、考核方式；R4 保留实验室名称、实验室简介、研究方向、科研成果、学生典型事迹、教师主页。
- 青禾招募通知中的报名截止、报名材料、提交邮箱与选拔流程归 R3，因为它们是特定实验室的招募流程；本次实验室招募不使用 R5，R1 只负责一般通知与办事渠道。
- 同名实验室但联系人、地点或课题组不同的记录不合并；原文"无"按缺失信息处理，不补造。
- R2 是课内培养安排，R5 是课外科研与竞赛机会。竞赛报名通知即使过期仍归 R5，不因过期改判 R1。
- "进实验室能算创新学分吗""推免要求实验室经历吗"含明确资格或加分意图，分别归 S1、S3，不归 S4。
- "推免要求竞赛经历吗""竞赛获奖在推免时加多少分"问的是推免条件或计分口径，归 S3，不因为出现"竞赛"改判 S1。只有明确问"创新学分"或"综测加分"时才回到 S1。
- "奖学金通知在哪看""推免通知在哪看"问的是通知渠道，归 S4 的 R1，不按奖学金或推免政策本身作答。

### 7.2 必要条件与追问

| 情形 | 处理 |
| --- | --- |
| 只说"学院有什么资源""资源怎么找" | 追问资源类别：培养方案与课程、实验室与科研团队、竞赛与科研实践、通知与办事渠道 |
| 说"某个实验室"但没说目的 | 追问是了解研究方向，还是了解怎么报名进实验室 |
| 问"学院有哪些实验室"、问某实验室研究什么 | 默认不再追问，直接查资料；若库内存在多个相关历史批次且无法确定唯一批次，改问年度 |
| 问怎么报名 | 默认不再追问，直接查资料；报名按 §7.4 的年度口径处理，不进入多批次追问例外 |
| 问"我能不能进 X 实验室" | 不追问年级、姓名或学号，也不判定个人资格；只按资料回答接收条件与对象 |
| 问培养方案或课程，未说专业或年级 | 追问"哪个专业、哪一级的培养方案" |
| 问学院通知、办事渠道、办公室电话、竞赛报名入口 | 类别已明确，不追问 |

S4 不追问年度、学期、姓名、学号或学院：年度只影响通知是否已截止，属于回答内容；系统不接入个人档案。

例外只有两类（2026-11-27 组长确认），其他 S4 场景继续遵循上面的不追问规则：

1. 公开实验室名录、研究介绍存在多个相关历史批次且无法确定唯一批次时，追问年度。
2. 历史联系人存在多个不同年度批次且联系人不同时，追问年度。

S4-03 的接收条件问题不适用上述两类例外：未写年度且只有历史招募通知时，直接证据不足，不追问年度。

### 7.3 证据适用性

S4 片段必须同时满足：

1. `retrieval_status=enabled`、来源核验通过、人工审核标记严格为 `true`，且片段与元数据的标题、来源、发布与生效日期一致。
2. 元数据 `business_direction_codes` 含正式代码 `COLLEGE_RESOURCES`。不能因为标题出现"实验室"就自行认作 S4 资料。
3. 资料类别与问题类别匹配，定类只取 `category_name`。标题或正文出现"实验室"不自动认定为 R3；问招募却只命中 R4 历史介绍、问研究方向却只命中 R3 报名通知，都拒绝；正文出现"电话"也不会把 R4 改成 R6。
4. 适用对象：R1、R2、R3、R5 必须提供 `applicability_raw`；字段缺失即不适用。R4 公开介绍可不强制。R6 豁免适用对象。
5. 适用字段统一使用五个中文核心键：`适用年级`、`适用专业`、`适用对象`、`学院`、`适用届别`。规则暂时保留 `grade`、`major`、`target` 等旧键兼容；同一含义的中文键与旧键同时存在且值不一致时，判为冲突、直接拒绝，不自行选择其中一个；需人工复核后重新入库。
6. 用户明确说了年级或专业，而资料缺少对应字段时 fail-closed，不因为句子里没有"我"就放行。
7. 联系方式只回答官方页面原文，不补电话、邮箱、报名条件、招生名额；实验室联系人必须来自 R3 片段，不能拿 R4 介绍或教师个人邮箱充当学院公开联系方式。

### 7.4 历史、过期与招募口径

- R3 招募通知按年度适用：问题写了明确年度（含今年、去年、前年）时，必须与通知的适用年度一致；同年度可回答报名流程、条件与计划人数，跨年度一律拒绝。问题没写年度时，按库内单一年度通知处理，并在答案中声明年度。R4 研究方向与公开介绍、R6 学院公开信息与联系方式不套用这条年度规则。
- 旧联系方式、旧培养方案处于 `HISTORICAL`/`EXPIRED` 时，本轮写“现在/目前/当前”一律拒绝；`SUPERSEDED` 资料只在本轮明确问旧版时可用。上一轮历史消息里的“去年”“旧版”“以前”不能替代本轮时间口径。
- 问"某实验室研究什么""学院有哪些实验室"：历史介绍或名录仍可回答内容，但不得写成"当前正在招募"。
- 问"怎么报名进实验室"：过期通知可以按 `historical` 回答流程，并说明本年度报名已截止、新年度通知待发布。
- 问"现在还招吗"：过期通知只能回答"本年度已截止"，不得表述为仍在招募。
- 问"现在还剩几个名额""现在招几个"：过期或历史通知一律不作为当前名额依据，返回证据不足。名额、接收人数、考核条件都是当年度信息，不能跨年沿用。
- 问"2026年当时招几个学生""当年计划接收几人"：这是年度计划人数，不是当前剩余名额，可按 `historical` 回答，并注明是当年度计划。
- 资料已被新版本替代时，只能回答历史问题并说明已被替代；问现行版本而只有旧版时证据不足。
- 知识库没有该实验室、没有该资源类别，或只有未审核资料时，统一回答"目前没有可依据的已审核资料"，不追问掩盖资料缺口。

### 7.6 未决与交接

- 新资料统一使用五个中文核心键 `适用年级 / 适用专业 / 适用对象 / 学院 / 适用届别`；规则暂时保留 `grade/major/target` 旧键兼容。同一含义同时出现中文与旧键且值不一致时，判为冲突并拒绝使用，需人工复核后重新入库。

- 工作流当前只接受 `timeliness=current`。S4 过期通知按 `historical` 作答需要吴诗莹放开该门槛；规则侧已放行历史通知作为历史证据，最终 `answer_mode` 由工作流按资料时效标注。

- S4 设计依据见 [S4 对接确认单-林彦翔](S4对接确认单-林彦翔.md)；回填结论、A/B/C 条目与六类边界以该单和本文为准。

### 9.1 交 Agent 工作流实现

规则落在既有注入点，不改公共模型与状态值：

| 注入点 | 本文件对应 | 实现要求 |
| --- | --- | --- |

### 9.2 交测试
