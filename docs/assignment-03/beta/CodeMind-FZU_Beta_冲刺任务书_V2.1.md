## 一、Beta 冲刺目标

在 Alpha 阶段已有的 FastAPI、AgentWorkflow、BM25 检索、业务规则、Qwen 适配、学生端和自动化测试基础上，补齐真实政策资料、历史政策处理、学院资源导航、受约束答案生成和前后端联调。

### 1.1 四大业务领域

| 编号 | 领域             | 本轮范围                                     |
|------|------------------|----------------------------------------------|
| S1   | 竞赛与科研信息   | 竞赛认定、创新学分、竞赛等级及相关政策咨询   |
| S2   | 奖学金与校园事务 | 奖学金类别、申请条件、评定流程及相关通知     |
| S3   | 推免与升学发展   | 推免资格、复试政策及相关条件咨询             |
| S4   | 学院资源导航     | 学院资源、实验室信息、报名流程及相关信息查询 |

S1—S4 均为 Beta 正式业务场景，必须纳入业务规则、检索测试和最终验收。

说明：

- S1—S4 是 Agent 业务场景编号，不是数据库业务方向代码。
- 数据库五大业务方向的实际 code 必须以仓库现有正式字典、初始化数据或已合并代码为准。
- 个人成长档案与长期规划属于后续迭代，不纳入本轮必做范围。

### 1.2 技术目标

- 整理、核验四大领域的知识资料。
- 区分现行政策与历史政策，避免将过期通知描述为当前有效。
- 完成 S4 学院资源导航业务规则。
- 以 LocalBM25Retriever / BM25 作为 Beta 正式检索基线。
- 完成真实资料检索、证据校验和引用展示。
- 完成真实 Qwen 调用及受约束自然语言答案生成。
- 由 Agent 校验模型返回的证据 ID，并根据真实检索片段构造 Citation。
- 补齐四领域端到端测试及模型异常、非法引用测试。
- 完成前后端真实 API 联调。
- 保证 Windows 本机环境可运行、可演示。

### 1.3 本轮暂不要求

- 云服务器部署、域名及备案。
- PostgreSQL 等数据库持久化改造。
- 完整管理端后端 HTTP API。
- 个人成长档案和长期规划。
- Embedding、Chroma、RRF 混合检索替换当前 BM25。
- Tavily 等联网检索能力。
- 通用 XLSX 文档解析接口。
- 缺乏官方资料支撑的实时信息推荐。
- ESP32 等硬件拓展。

### 2.2 Qwen 受约束生成约定

Beta 采用受约束的自然语言生成。

Agent 为本次请求中的合格证据分配临时 `evidence_id`，再将问题和证据交给 Qwen。Qwen 必须返回严格 JSON 内容：

``` json
{
  "answer": "基于已提供证据形成的自然语言回答。",
  "used_evidence_ids": ["E1", "E2"]
}
```

要求：

- `evidence_id` 由 Agent 在当前请求内分配，不是数据库业务方向代码。
- Qwen 只能引用本次提示中提供的证据 ID。
- Qwen 不得自行创建 Citation、来源 URL、文件名或发布日期。
- Agent 必须验证 JSON 格式、答案非空、证据 ID 存在且属于本次通过门禁的证据集合。
- Agent 根据证据 ID 映射到真实 `RetrievedChunk`，再由 Agent 自身构造 Citation。
- 非法 JSON、未知证据 ID、跨请求证据 ID、空答案或无法核验的输出不得直接进入最终回答。
- 证据不足时按既有状态返回 `insufficient_evidence`。
- 证据 ID 校验只能证明引用指向真实片段，不能单独证明答案中的每项事实均受原文支持；仍须检查回答与原文的一致性。

该协议只约束 Agent 与 Qwen 的内部调用，不改变 `LLMGenerateRequest`、`LLMResult` 或学生端 HTTP 响应结构。

### 2.3 检索技术边界

- Beta 正式验收基线为 BM25。
- 不要求本轮增加 Embedding、Chroma 或 RRF。
- 不得把 PPT 中的候选技术路线描述为已经实现。
- 检索命中不代表资料可以直接用于正式回答，仍须通过来源、审核、时效和适用范围检查。

### 2.4 资料审核红线

当前正式 `approved/` 资料目录是否已有人工审核通过的 DocumentPackage，开工前须由资料负责人和组长再次核实。

资料阶段：

| 阶段          | 含义                                       | 是否允许正式问答   |
|---------------|--------------------------------------------|--------------------|
| `processing/` | 待整理、待核验资料                         | 否                 |
| `processed/`  | 已完成解析或技术处理，仍需审核             | 否                 |
| `approved/`   | 完成来源、适用范围、时效核验及最终人工审核 | 满足开放条件后允许 |

注意：

- 合成测试资料、待审核资料不得冒充正式政策资料。
- 资料进入正式检索范围前必须完成来源、适用范围、时效及人工审核。
- 资料负责人负责整理和技术核验，项目负责人罗宇泽负责最终人工审核。
- 解析成功、索引成功均不等于审核通过。

### 2.5 XLSX 资料处理边界

丁晓炜需要处理青禾计划实验室需求 XLSX 附件，但本轮不新增通用 XLSX 解析接口。

统一流程：

1.  保留原始 XLSX 文件。
2.  提取表格内容并人工检查。
3.  将核验后的有效信息整理为 Markdown/TXT。
4.  保留原始文件名、来源、必要的校验信息及转换说明。
5.  核对实验室名称、研究方向、联系方式、适用对象和报名流程。
6.  转换后的 Markdown/TXT 再进入现有文档解析和知识库流程。
7.  转换或解析成功不代表资料已经通过人工审核。

**11 名成员并行开发 + 组长统一接口管理 + 按依赖关系分批合并 PR + 集中集成验收。**

1.  修改范围与个人分工一致。
2.  不违反 V2.1-Final 公共接口规范。
3.  测试命令和实际输出明确。
4.  不引入明显回归。
5.  上下游依赖已经满足，或已明确标注尚未完成的集成部分。
6.  真实资料、合成测试资料和 Mock 数据有清晰区分。

### 6.1 最终必须保留的证据

- GitHub 合并记录。
- 自动化测试结果。
- 正式资料审核记录。
- 真实模型调用记录。
- Qwen 非法输出和引用校验测试记录。
- 四领域运行截图。
- 浏览器及手机端回归记录。
- 本机运行说明。
- Beta 最终验收报告。

### 6.2 最终验收原则

- 四个领域均有明确的真实资料或合理拒答路径。
- 正式回答的引用能够追溯到真实资料。
- 历史政策不会冒充当前政策。
- 模型不能自行创造来源和引用。
- 证据不足时能够正确拒答。
- 系统能够在 Windows 本机稳定启动和演示。
- 不得将未实现的远期规划写成已完成成果。

## 七、团队协作原则

1.  所有成员对自己负责的任务和交付物负责。
2.  遇到接口问题优先沟通，不擅自修改公共契约。
3.  发现阻塞任务应及时向组长反馈。
4.  每次站立会议控制在 10 分钟左右，只汇报进度、问题和下一步计划，不在会议中展开技术细节。
5.  所有功能以真实代码、实际运行和测试证据为准。
6.  不为了赶进度降低政策资料审核和证据校验标准。
7.  不要求所有成员排队开发；允许并行开发，但必须遵守依赖关系。
8.  项目负责人统一管理公共接口、PR 审核、合并节奏和最终验收。

**Beta 冲刺的最终目标不是简单增加功能数量，而是让 CodeMind-FZU 从 Alpha 阶段的基础问答系统，进一步成为能够依据真实资料、理解业务条件、正确追问、生成受证据约束的自然语言回答并提供可追溯依据的校园事务与发展信息 Agent。**
