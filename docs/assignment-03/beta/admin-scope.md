# 管理端功能范围说明（Beta）

> 负责人：林彦翔　｜　版本：v1.0（2026-11-23）　｜　分支：`docs/beta-resource-navigation`
> 对应任务：《Beta 冲刺任务书 V2.1》§三.6 第 5—6 项「检查现有管理端原型、区分已实现和未实现的管理端功能」
> 结论：**本轮只做范围说明，不新增管理端后端 HTTP API，不做数据库持久化。**

本文件回答三个问题：管理端原型设计过什么、代码里实际实现了什么、哪些能力属于本轮明确不做的后续规划。

## 1. 两个口径

管理端存在两份互不对应的材料，必须先分清，否则会把「画过」当成「做完」：

| 口径 | 载体 | 数量 | 状态 |
| --- | --- | --- | --- |
| **设计态** | 第二次作业 Figma 后台原型，`docs/assignment-02/prototype/admin/screenshots/` | 24 张 | 设计完成，多数未实现 |
| **代码态** | `frontend/src/admin/`，Alpha 阶段 PR #28 合入 | 7 个 TS/CSS 模块 + 1 份演示数据 | 部分实现，前端可用 |

两条现成结论（Alpha 阶段已记录，本次复核仍成立）：

1. `backend/app`、`backend/services` 中**没有** admin 路由；只有 `backend/contracts/protocols.py` 里的 `DocumentAdminService` 协议（4 个方法）。
2. `frontend/src/shared/api.ts` 已封装 **5 个**后台接口调用，但后端一个都没实现，因此页面先请求真实接口、失败后降级到演示数据。

## 5. 与 S4 的衔接

1. **类别承载**：S4 六类直接作为资料的 `category_name` 取值。管理端不为它新增写死选项——`categoryOptions()` 按实际资料动态生成，补入 S4 资料后筛选下拉自动出现六类。
2. **证据门禁的上游**：S4 只能检索 `retrieval_status=enabled` 的资料，而「检索开放」正是管理端列表的第 7 列与四维筛选之一。管理端的状态维护就是 S4 能不能答的前置条件。
3. **当前无 S4 资料**：`data/documents.json` 是 Alpha 的 44 条演示数据，不含 S4 六类。因此管理端现在**看不到** S4 的筛选值，这是数据未补，不是功能未做。
4. **待办**：补入 S4 样例数据（R1—R6 各至少一条）后，类别下拉与统计卡才会体现六类。该数据补充不在本 PR 范围内。

## 6. 数据口径

- 演示数据 44 条的**描述字段**（名称、类别、发布单位、文号、来源链接、发布日期、适用范围、核查说明）来自第二次作业已合并的资料登记，可溯源。
- **状态字段是演示编排**：相对登记原值，来源核验改了 3 条、时效核验改了 32 条、检索开放改了 32 条，正文提取 0 条改动；每条记录保留 `seed_status` 与 `demo_rule`，可逐条回溯。
- 登记原始检索状态是 44 条全 `blocked`。
- 因此：管理端截图里的「已开放检索 3 条」是演示编排结果，**不是**真实核验结论，不能作为「资料已审核」的证据。
