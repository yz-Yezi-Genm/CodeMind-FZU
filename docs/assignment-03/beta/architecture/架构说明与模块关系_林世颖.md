## 3. 系统总体架构

对应图件：`系统总体架构图_林世颖.drawio` / `.svg` / `.png`。

分层与调用方向如下：

1. **学生端前端**通过 HTTP/JSON 访问 FastAPI 后端，负责问题输入、回答与引用展示、追问交互；管理端前端已落地原型交互，真实管理 API 不可用时降级前端模拟数据。
2. **FastAPI 后端**完成请求校验、会话管理、请求追踪、Agent 调用入口与错误处理，不直接编排业务规则。`main:app` 为契约骨架，`alpha:app` 在 lifespan 中构建真实运行时，`dev:app` 注入 Mock 服务供本地演示。
3. **公共契约层**由 `models.py` 与 `protocols.py` 构成，已落地的服务适配器、Agent 工作流、业务规则与本地检索均遵守其中的类型与协议边界。
4. **Agent 工作流与协作模块**包括 AgentWorkflow、业务规则、Retriever、QwenClient、会话管理与资料处理链路。四个业务场景共用同一套 AgentWorkflow、Retriever 与 Qwen 适配，不为每个场景设计独立系统。
5. **知识库资料阶段门禁**区分 `processing/`、`processed/`、`approved/` 三个阶段；解析成功或索引成功不等于人工审核通过，只有满足核验条件并经项目负责人最终人工审核的资料才允许进入正式问答。
6. 规划模块集中在灰区，与已实现部分在图中视觉区分。

后端与 Agent、Agent 与检索/模型之间使用 Python 类型化接口；浏览器与后端之间使用 HTTP/JSON，内部调用不额外引入 HTTP 服务。

| 编号 | 业务场景 | 对应数据库业务方向 | Beta 范围 |
| --- | --- | --- | --- |
| S1 | 竞赛认定（创新学分、综测加分） | 竞赛与科研信息 | 正式纳入 |
| S2 | 奖学金申请 | 政策与事务办理 | 正式纳入 |
| S3 | 推免条件咨询 | 升学与就业发展 | 正式纳入 |
| S4 | 学院资源导航 | 学院资源导航 | Beta 新增 |

S4 覆盖学院官方资源、办事渠道与公开信息查询，实验室名称、研究方向、报名流程及适用对象查询，官方培养方案与学习科研资源导航；资源信息缺失、来源不明或时效无法确认时提示并拒答。S4 不包含动态科研机会推荐、实时招生名额查询或未经官方资料支持的导师评价。

### 4.2 场景与方向的区分

- S1—S4 是 Agent 业务场景编号，不是数据库业务方向代码。数据库五大业务方向的实际 code 以仓库正式字典、初始化数据或已合并代码为准，不自行创造。
- `RetrievalRequest` 当前仅定义单个 `business_direction_code`，本轮不改为列表字段。问题涉及多个方向或方向无法可靠确定时，不猜测方向代码缩小检索范围，可以不传 `business_direction_code` 执行全库检索，再由 Agent 与业务规则按证据筛选。
- 多业务方向过滤若后续确有需要，先由项目负责人发起公共接口变更，成员不自行增加字段。

## 5. Agent 问答流程

对应图件：`Agent问答流程图_林世颖.drawio` / `.svg` / `.png`。

完整问答过程如下：

1. 学生在浏览器提交问题，后端通过 `POST /api/v1/ask` 接收 `query` 与 `conversation_id`。
2. 后端完成请求校验；会话存储按 `conversation_id` 读取历史，构造 `AgentRequest` 交给 Agent 工作流。前端只传会话标识，不传递自行拼接的历史消息作为可信上下文。
3. Agent 识别 S1—S4 业务场景。
4. 检查必要信息：信息不充分时返回 `needs_clarification` 与 `clarifying_question`，每轮最多追问一个问题；追问阶段不调用 Retriever 和 Qwen。
5. 信息充分后调用 `Retriever.retrieve()` 检索知识片段；方向不确定时不传方向代码，执行全库检索。
6. 对候选片段执行来源、适用范围、审核状态与时效检查（证据门禁）。
7. 只将通过门禁的合格证据交给 Qwen，按受约束生成流程处理（见第 6 节）。
8. Agent 校验模型输出。
9. Agent 根据真实检索片段构造 Citation。
10. 生成 `AgentResult`，由后端包装为统一 `AskResponse` 返回前端；前端展示回答、引用与 warnings。

### 5.1 历史政策处理口径

历史资料不等于无效证据：对应年度办理周期已结束、但真实有效的已审核资料，可以回答历史情况，但必须标注 `historical`；历史资料可以回答历史问题，不能作为现行政策或当前办理依据。

| 资料情况 | 处理方式 |
| --- | --- |
| 当前有效的通用政策 | `current_policy` |
| 当前正在办理的年度通知及流程 | `procedure_reference` |
| 已结束的年度通知 | `historical` |
| 已被新版本替代的旧政策 | `historical`，并说明已被替代 |
| 无法确认是否为现行版本 | `insufficient_data` |
| 来源未核验、`retrieval_status` 不为 enabled | 拒绝使用 |
| 年度不匹配 | 按业务规则拒绝或追问 |

证据门禁对所有回答模式都要求：`retrieval_status=enabled`、`source_verification_status=verified`、人工审核标记严格为 true、已有发布日期与生效日期不在未来、文档版本与片段身份一致、适用范围与时效信息足以支撑当前回答。`pending`、`uncertain`、`failed`、`blocked`、`review_only` 状态不能放行。

> 当前 main 的工作流尚未完成上述历史政策对齐（见 2.2），本节描述的是 V2.1-Final 目标口径；最终修订稿将在改造合并后核对落地状态。

## 6. Qwen 受约束生成与证据校验

对应图件：`Qwen受约束生成与证据校验流程图_林世颖.drawio` / `.svg` / `.png`。

### 6.1 处理顺序

1. 证据门禁通过的合格片段集合进入生成流程。
2. Agent 为本次请求中的可用证据分配临时 `evidence_id`（E1、E2…），并保存 `evidence_id` 与真实 `RetrievedChunk` 的映射；映射仅在本次请求内有效。
3. 组装 `LLMGenerateRequest`：用户问题与带 `evidence_id` 的证据一并交给模型；未通过门禁的资料不得进入模型上下文。
4. Qwen 根据问题和给定证据生成自然语言答案，返回严格 JSON，不使用 Markdown 代码围栏：

```json
{
  "answer": "基于已提供证据形成的自然语言回答。",
  "used_evidence_ids": ["E1", "E2"]
}
```

5. Agent 校验：JSON 可解析、`answer` 非空、`used_evidence_ids` 非空、ID 存在且属于本次通过门禁的证据集合。
6. 校验通过后，Agent 将 ID 映射回真实 `RetrievedChunk`，再由 Agent 自身构造 Citation；模型不自行创建 Citation，不填写来源 URL、文件名或发布日期。
7. 校验失败时按安全回退策略处理：非法 JSON、空答案、不存在的 ID、跨请求 ID、无可用证据 ID 等情况，不直接返回模型生成内容；无法形成可靠答案时返回 `insufficient_evidence`，`citations` 为空。

### 6.2 边界说明

- `evidence_id` 是 Agent 与 Qwen 之间的内部协议，不是数据库业务方向代码，也不是新增的学生端 HTTP 字段；该约定不改变 `LLMGenerateRequest`、`LLMResult` 或学生端 `AskResponse` 结构。
- 模型只能返回本次提示中提供的 `evidence_id`；Agent 必须验证 ID 存在且属于本次门禁集合。
- 证据 ID 校验只证明引用指向真实片段，不单独证明回答中的每项事实都被原文支持；答案与原文一致性仍须通过测试核验，不能宣称仅凭 ID 校验即可消除幻觉。
- 模型常识补充或无来源推断不得作为正式政策结论；证据只能支持部分问题时，回答必须明确限定范围。

### 8.1 规范与代码差异反馈项

以下事项已核对，按规范第十六章先反馈组长确认，不在本轮自行修改公共接口：

1. **Retriever Protocol 缺方法声明**：`LocalBM25Retriever` 已实现 `get_document_metadata` 与 `get_parsed_chunk`，但 `protocols.py` 的 `Retriever` Protocol 尚未纳入这两个方法；规范 8.4 要求补齐公共协议与契约测试。
2. **管理元数据更新协议缺口**：前端 `api.ts` 与接口契约已定义 `PATCH /api/v1/admin/documents/{document_id}` 元数据更新接口，但 `DocumentAdminService` Protocol 尚未定义对应元数据更新方法；待后端接口统一时补齐，本轮不改动其他成员负责的后端代码。
3. **工作流历史政策口径与规范第九章不一致**：属 Beta 待开发项（吴诗莹负责），非既有接口破坏；改造完成后须以真实资料结构与自动化测试验证，不能仅修改一个状态判断即宣称完成。
4. **当前抽取式证据协议与规范 11.3 不一致**：属 Beta 待开发项；受约束生成改造合并后，工作流提示词、校验逻辑与测试用例需同步更新。

## 9. 设计约束与边界

- 各模块导入公共模型与 Protocol，不在各自模块中重复定义相同 DTO；公共字段、类型、路径、状态值与函数签名的变更须先报组长统一确认。
- 文档完成解析、入库或建立索引，不等于政策已核验，也不等于可以进入正式问答检索；开放检索须满足核验条件并经独立人工审核流程确认。
- 当前尚未完成认证授权接入，管理端 API 不能对公网暴露；前端隐藏按钮不构成权限控制。
- 模型 API Key 只从环境变量读取，不写入源码、文档、日志或 Git 历史；不向浏览器传递密钥、数据库连接串、内部堆栈或本地绝对路径。
- 浏览器不直接访问数据库或检索存储。
- 内存会话与内存索引仅用于当前阶段联调，不构成持久化存储方案；跨进程持久化在后续部署阶段另行设计。
- 检索命中不等于资料可用；BM25 结果仍须经过 Agent 业务规则与证据门禁。
