# S4 学院资源导航设计

> 负责人：林彦翔　｜　版本：v1.12（2026-11-28）　｜　分支：`docs/beta-resource-navigation`
> 依据：《Beta 冲刺任务书 V2.1》§三.6、《Beta 接口规范 V2.1-Final》§4.2 与 §7.4
> 下游：雷葭雨《Beta 业务规则》§7（`docs/assignment-03/beta/business-rules.md`）

本文件定义 S4「学院资源导航」的产品设计：资源分几类、每类要展示什么、学生真实会怎么问、哪些能答、哪些不承诺。

**本文只写产品侧口径，不写判定规则、不写代码。** 判定条件、追问实现与证据门禁以规则侧文档为准；本文的六类标签与 `category_name` 取值已与其对齐，不另立一套。

---

## 1. 结论摘要

| 项 | 结论 |
| --- | --- |
| 资源分类 | 六类，类名同时作为资料 `category_name` 的取值 |
| 信息结构 | 12 个字段分四层：学生端正文、Citation、内部元数据、管理端专用；本轮不新增 HTTP 字段 |
| 典型场景 | 23 个：S4-01—S4-16 与规则侧测试用例编号一致，S4-17—S4-20、S4-22—S4-24 为本设计补充并经规则侧与组长确认；每个场景区分「目标验收预期」与「当前可运行预期」 |
| 可答范围 | 资源名录、研究方向、报名流程（按历史口径）、培养方案、选课辅修、通知栏目、办事入口 |
| 不承诺 | 实时名额、实时招募状态、导师评价、个人录取判断、无官方出处的联系方式、按人数或绩点筛选 |
| 资料缺口 | R6 无审核资料；R1 栏目未全部入库；R2 只有历史方案；R3/R4 青禾包待审核入库；R5 仍为 pending |

## 2. 资源分类

### 2.1 六类总表

| 编号 | 资源大类（= `category_name`） | 二级子类 | 判类边界 | 现有官方资料 |
| --- | --- | --- | --- | --- |
| R1 | 通知与办事渠道 | 通知公告 / 办理流程与材料 / 办事入口 | **按内容判**：通知、办理流程、材料、入口都归 R1；其中通知有发布日期与办理窗口，**栏目目录与常设入口以更新或核验时间代替办理窗口** | 学籍与学生事务 4 条、课程考试与教务办理 13 条（含办法与通知） |
| R2 | 培养方案与课程 | 培养方案 / 课程与选课 / 辅修与学分认定 / 通识与在线课程 / 学位要求 | **学什么、修多少、怎么选、能否替代** | 培养方案与学位要求 8 条（5 条历史培养方案 + 2 条学位细则 + 1 条数智实验班）；另有选课、辅修、课程替代办法 |
| R3 | 实验室与科研团队 | 名录 / 接收条件与人数 / 报名与考核 / 地点与联系人 | **谁、在哪、谁能进、怎么进、找谁** | 青禾计划实验室需求一览表：24 条记录 + 报名通知 |
| R4 | 研究方向与公开介绍 | 方向与简介 / 成果与典型事迹 / 教师主页 | **研究什么、有什么成果、去哪看官方介绍** | 同一份一览表的简介与科研成果字段 + 教师主页链接 |
| R5 | 科研实践与竞赛 | 本科生科研项目 / 竞赛报名与目录 / 创新学分与奖励 | **课堂外可参与的机会** | 开放探索性实验通知、蓝桥杯报名、科创竞赛奖励办法、创新学分认定办法 |
| R6 | 学院公开信息与联系方式 | 学院与系所简介 / 办公地点电话邮箱 / 官网入口 | **长期有效、无办理窗口** | 暂无成体系资料，仅有学院官网候选页面待审核 |

### 2.2 边界规则（判类的全部依据）

1. **R1 与 R6**：**先按内容判，再按时效判**。内容是通知、办理流程、材料、办事入口 → R1；内容是学院与系所简介、办公地点、公开电话邮箱、官网入口 → R6。同一 URL 只归一类。R1 内部再分「时效性通知」与「常设栏目目录」：后者没有办理窗口，以更新或核验时间代替，**不因此改判 R6**。**实验室层联系人归 R3，不归 R6**；R6 只收学院、系所、办公室层面的公开联系方式。
2. **R3 与 R4**：R3 答「组织与入口」，R4 答「内容与方向」。青禾计划中同一条实验室记录同时含两类信息，**拆成 R3、R4 两条资源**，分别落两个资料包；不能把整条记录强行归为单一类别。
3. **R2 与 R5**：R2 是培养方案内的课程与学分要求，R5 是课堂外可参与的项目与比赛。**竞赛报名通知即使已过期仍归 R5**，不因过期改判 R1——时效由字段体现，不改类别。

补充两条既定口径：

- 青禾招募通知中的报名截止、报名材料、提交邮箱与选拔流程归 **R3**（它们是特定实验室的招募流程）；本次实验室招募不使用 R5。
- 同名实验室但联系人、地点或课题组不同的记录**不合并**；原文「无」按缺失处理，不补造。

### 2.3 与既有原型的对应

第二次作业的学生端「学院资源」结果页只有 4 个入口，六类是它的细化，不需要重画页面：

| 旧入口 | 对应类别 | 说明 |
| --- | --- | --- |
| 01 培养方案 | R2 | 直接对应 |
| 02 教师与科研方向 | R4（含 R3 的「找谁」） | 方向与团队信息合并展示 |
| 03 实验室与项目 | R3 + R5 | 招募、报名归 R3，课外项目与竞赛归 R5 |
| 04 通知与办事入口 | R1 + R6 | 有时效的通知归 R1，长期有效的联系入口归 R6 |

### 2.4 与数据库七类字典的关系

数据库 `knowledge_categories` 的七类（学籍与学生事务、课程考试与教务办理、综评与奖学金、竞赛认定与创新学分、培养方案与学位要求、科研实践与实验室、推免与升学）**保持不变，不做一对一映射**。

S4 六类作为 `category_name` 的资源细分类值独立使用；管理端按资料实际取值动态生成筛选选项（`frontend/src/admin/filters.ts` 的 `categoryOptions()`），补入 S4 样例数据后即可显示。PG 持久化阶段再单独设计正式映射或独立子类字段。

## 3. 资源信息结构

### 3.1 信息层级、字段与数据来源

先明确边界：下面 12 个字段是**设计完整性清单**，不是现有接口的能力承诺。学生端只拿到 `AskResponse`（`answer`、`citations`、`warnings`、`answer_mode`、`status`），本轮不新增任何 HTTP 字段。字段按四层划分：

| 层级 | 内容 | 学生端是否可见 |
| --- | --- | --- |
| A 回答正文 | 资源名称、类别、简介、适用对象、方向或用途、来源名称、发布或更新时间、当前有效性、联系方式、不完整声明 | 可见，全部由 `answer` 文本承载 |
| B 引用信息 | 文档/版本/片段 ID、标题、发布单位、来源链接、发布与生效日期、定位、原文摘录、来源与时效核验状态、检索状态 | 可见，全部由 `citations` 承载 |
| C 内部元数据 | `applicability_raw`、`deadline_on`、`policy_status`、`record_code`、`version_no`、`document_type`、`category_name`、`business_direction_codes`、`extraction_status`、`v1_inclusion_status`、`temporal_notes` | 不可见，只用于检索、门禁与审核 |
| D 管理端专用 | `DocumentSummary.updated_at`、文件清单、演示数据的 `seed_status` / `demo_rule` | 不可见，只在管理端列表与详情使用 |

字段来源与归属：

| 来源模型 | 提供什么 | 归属层级 |
| --- | --- | --- |
| `DocumentMetadata` | 标题、类别、来源、发布/生效日期、适用对象、核验状态 | A、B、C |
| `ParsedChunk` | 片段正文、`locator`、`original_locator` | A、B |
| `Citation` | 引用卡片所需字段，是 `DocumentMetadata` + `ParsedChunk` 的子集 | B |
| `DocumentSummary` | 列表摘要，含 `updated_at` | D，学生端答题链路不经过它 |

12 个字段的映射：

| # | 展示字段 | 数据来源 | 学生端承载方式 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | 资源名称 | 实验室名称取 `ParsedChunk.content` 原文；`DocumentMetadata.title` 是**资料包标题** | 正文（实验室名）＋ `Citation.title`（包标题） | 两者不能混用，见下方「资源名称的三层对应」 |
| 2 | 资源类别 | `DocumentMetadata.category_name`（C 层） | 正文表述 | 学生端没有独立类别字段，只出现在回答文字里 |
| 3 | 资源简介 | 片段正文 | 正文 | 取资料原文，不生成概述 |
| 4 | 适用对象 | `applicability_raw` 五键（C 层） | 正文表述 | `applicability_raw` 本身不暴露给学生端 |
| 5 | 研究方向或具体用途 | 片段正文 + `document_type` | 正文 | R4 必填，其余可选 |
| 6 | 官方来源 | `publisher`、`source_url`（B 层）；`responsible_department`、`document_number`（C 层） | 正文来源名 + `Citation.publisher` / `Citation.source_url` | 文号和责任部门只在内部与审核使用 |
| 7 | 原始链接或文件 | `source_url`（B 层）；`DocumentPackage.files`（C/D 层） | `Citation.source_url` | 附件缺失必须在答案正文中说明 |
| 8 | 发布日期或更新时间 | 发布与生效日期取 `DocumentMetadata` 的 `published_on`、`issued_on`、`effective_on`（B 层）；更新时间取 `DocumentSummary.updated_at`（D 层） | 发布日由 `Citation.published_on` / `effective_on` 承载；更新时间**不进入学生端** | `DocumentMetadata` 与 `ParsedChunk` 均无 `updated_at` |
| 9 | 当前有效性 | `policy_status`、`deadline_on`（C 层）、`timeliness_verification_status`（B/C 层） | 正文四档表述 + `Citation.timeliness_verification_status` | 展示时归并为现行有效 / 历史参考 / 已截止 / 无法确认，原始状态值保留 |
| 10 | 核验状态 | `source_verification_status`、`retrieval_status`（B/C 层） | `Citation` 两个状态字段 | 未核验或未开放的资料不进入正式问答 |
| 11 | 联系方式 | 片段正文中的联系人、电话、邮箱 | 正文 | 仅官方资料原文中存在时展示，时效判定见 4.4 |
| 12 | 依据定位 | `locator`、`original_locator`（B 层） | `Citation.locator` / `Citation.original_locator` | 支撑引用追溯到具体片段与行 |

**资源名称的三层对应**：

1. **资料包标题** = `DocumentMetadata.title`。青禾 R3、R4 各是一个资料包，标题是整份材料的名称（以入库时登记为准，例如「青禾计划实验室需求一览表（R3 招募条件）」），**不是**单个实验室名称。
2. **具体实验室名称** = `ParsedChunk.content` 中的原文名称，用于回答正文。不能把包标题当作实验室名称。
3. **原文定位** = `locator` / `original_locator`（如「实验室需求一览表·第14行」），用于引用与复核。

**同名实验室的区分**：以 XLSX 的 `序号` 为唯一标识，辅以地点、课题组、联系人区分；「EDA创新实验室」在序号 14、15 各有一条，「EDA」还有序号 24，「空间数据挖掘与信息共享教育部重点实验室」在序号 8、18 各有一条（后者属「高嘉良课题组」）。**名称相同不合并**，引用时用 `locator` 指向具体行。

**模型输入边界**：`agent_generation.py` 的 `generation_request()` 只把问题、历史、以及每条证据的 `evidence_id`、片段正文 `content`、`answer_mode` 传给模型，**不传完整元数据**。因此回答里的类别、适用对象、联系方式等信息必须来自片段正文，不能依赖模型读元数据。

### 3.2 入库必填与缺失处理

本节是**资料整理与入库审核**的要求，不是运行时门禁清单：某字段标「必填」只表示缺了就不能作为正式资料入库，不代表系统在运行时一定会拦截。运行时实际执行的检查见 3.3。

| 类别 | 必填字段 | 缺失时 |
| --- | --- | --- |
| R1 | 名称、类别、来源、适用对象、正文；通知类另需发布日期与办理窗口 | 缺适用对象即不适用；通知类缺日期不适用；栏目目录类以更新时间代替 |
| R2 | 名称、类别、来源、适用年级、适用专业、正文 | 不适用；问培养方案必须带年级或专业 |
| R3 | 名称、类别、来源、适用对象、接收条件、报名方式 | 不适用；联系方式须标年度来源，判定见 4.4 |
| R4 | 名称、类别、来源、简介或研究方向 | 缺简介与方向即不适用；**不强制适用对象** |
| R5 | 名称、类别、来源、适用对象、参与或报名方式 | 不适用 |
| R6 | 名称、类别、来源、官方出处 | 不强制适用对象；无官方出处直接拒答 |

统一规则：

- 用户明确说了年级或专业、而资料缺少对应字段时，按「无法核实」处理，不因句子里没有「我」而放行。
- 联系方式不做字段级校验，由引用兜底：回答中出现电话、邮箱、地点时，引用必须指向含该信息的原始片段。
- 展示字段只允许来自已审核资料原文，不允许由模型补全或改写。

### 3.3 运行时证据门禁（以规则侧为准）

入库必填 ≠ 运行时强制。运行时真正执行的门禁以 `business-rules.md` §7.3、§7.4 为准，产品侧只关心它带来的可见后果：

| 门禁 | 来源 | 产品可见后果 |
| --- | --- | --- |
| `retrieval_status=enabled` | 规则侧 §7.3 第 1 条 | 未开放检索的资料一律答「没有可依据的已审核资料」 |
| 来源核验通过 + 人工审核标记严格为 `true` | 规则侧 §7.3 第 1 条 | `pending` / `review_only` 资料不进入回答 |
| 元数据与片段一致（标题、来源、日期） | 规则侧 §7.3 第 1 条 | 元数据与正文对不上时整条拒绝 |
| `business_direction_codes` 含 `COLLEGE_RESOURCES` | 规则侧 §7.3 第 2 条 | 只挂其他方向的资料不会被当 S4 资料 |
| `category_name` 与问题类别匹配 | 规则侧 §7.3 第 3 条 | 问招募只命中 R4 介绍时拒绝，不混答 |
| R1/R2/R3/R5 有 `applicability_raw`；R4 不强制、R6 豁免 | 规则侧 §7.3 第 4 条 | 缺适用对象即证据不足 |
| 官方来源主机校验 | 规则侧 §7.3 域名白名单 | R6 只认 `ccds.fzu.edu.cn`；公众号需核验记录 |
| 年度口径：R3 同年度可答，跨年度拒绝；历史/过期资料遇「现在/目前」拒绝 | 规则侧 §7.4 | 决定了 S4-01、S4-02、S4-22、S4-07、S4-08、S4-13—S4-15、S4-18 的结果 |

由此得出两条边界，写进文档以免承诺超出实现：

1. **本文 3.2 的必填项不全是运行时拦截项**。例如「原始文件登记」「更新时间」缺失不会导致运行时拒答，但会造成溯源或展示不完整；反过来，来源核验与人工审核状态是运行时额外检查，不是填了字段就能替代。
2. **展示能力不等于校验能力**。本文规定的「联系人带年度」「列表不完整要声明」属于回答组织要求，运行时不会自动拦截，需由规则侧 §7.3、§7.4 与引用校验共同保证。

### 3.4 `applicability_raw` 键名

新资料统一使用五个中文核心键，与既有 S1—S3 入库资料保持一致：

| 键 | 取值示例 |
| --- | --- |
| `适用年级` | 全体本科生 / 大二至大四 / 2024级 |
| `适用专业` | 计算机与大数据学院各专业 |
| `适用对象` | 本科生 |
| `学院` | 计算机与大数据学院（软件学院） |
| `适用届别` | 2027届 |

规则侧暂时保留 `grade` / `major` / `target` 旧键兼容；同一含义的中文键与旧键同时存在且值不一致时判冲突并拒绝，需人工复核后重新入库。

### 3.5 资料来源的附加核验信息

微信公众号等非标准域名来源的核验记录写入 `temporal_notes.wechat_verification`（包含账号名称、账号 ID、核验依据）。该结构**只作为入库核验信息，不是学生端展示字段**，也不作为 S4 回答内容。

### 3.6 展示规范

1. **一条资源一条引用**：回答中每列出一项资源，就必须有一条指向该资源原文的引用；`Citation` 的 `source_url` 与 `excerpt` 都必须非空。
2. **时效必须显式声明**：过期的年度通知要写明具体学年、「报名已截止」与截止日期，不得表述为「正在招募」。
3. **四条禁止表述**：不得说「正在招募」；不得说「还有名额」；不得评价导师或实验室优劣；不得给出个人能否被录取的结论。
4. **不完整要承认**：一次只能列出检索命中的前 K 条时，末行单独写「共 24 条实验室记录，本次展示 K 条，完整表见来源」，不得让读者误以为列表完整。
5. **资料不足时说明缺什么**：例如「目前没有该实验室的已审核资料」，而不是「没有这个实验室」。
6. **联系人必须带年度**：实验室联系人要标注所属年度与报名状态，不得表述为「当前联系人」；时效无法确认时不展示，判定见 4.4。
7. **分段格式**（2026-11-26 与学生端确认）：每项资源以实验室名称开头，资源之间空一行，末行单独写统计句；本轮用纯文本分段，不做列表或卡片改造。
8. **历史提示去重**（同日确认）：保留 `answer_mode` 的「历史资料参考」标签，正文保留具体学年与「报名已截止」；`HISTORICAL_POLICY` 若与正文是同一句，只展示一次；若警告补充了「联系方式为历史信息」「新一轮招募状态尚未确认」等信息，则保留展示。前端当前逐条展示 `warnings`，去重属于展示规则，不改接口。

### 3.7 批次枚举能力与边界（2026-11-27 组长决策）

S4 判断「库内同一事项有几个历史批次」依赖检索层的两个只读扩展方法。它们是 `LocalBM25Retriever` 上的**可选能力**，Beta 阶段**不升格到公共 `Retriever` Protocol**，公共契约保持不变。

| 能力 | 方法 | 用途 |
| --- | --- | --- |
| 按条件枚举已开放资料 | `list_document_metadata(subject=None, business_direction_code=None, category_name=None)` | 取候选版本及其元数据 |
| 按版本取片段 | `list_parsed_chunks(version_id=…)` 或 `list_parsed_chunks(record_code=…, version_no=…)` | 取跨年度批次正文，比较联系人是否一致 |

调用约束：

1. 业务层必须用 `getattr` 检查方法是否存在。**方法不存在 = 当前检索器不具备完整批次枚举能力**，此时不得假定库内只有一个批次，也不得据此放行历史回答，应返回证据不足。
2. **方法存在但返回 `[]` = 枚举成功、没有符合条件的已审核资料**。这与「方法不存在」是两种不同情况：前者是「没有资料」，后者是「无法判断」，回答里的说明必须区分。
3. 枚举顺序：**先按 `business_direction_code=COLLEGE_RESOURCES` 与对应 `category_name` 枚举完整候选**，再在业务层按实验室名称及别名匹配。**不得只凭 `subject` 子串的返回结果证明库内只有一个批次**。
4. `subject` 只用于缩小候选，不承担别名扩展；名称比对与别名表由业务层负责。

批次归并口径（2026-11-28 组长补充）：

- **批次默认按适用年度归并**。
- **同一适用年度内，只有原始资料明确标注了不同批次（如「第一批」「第二批」）时，才把它们算作两个独立业务批次**。批次标识为「适用年度 + 原始标注的批次名」。
- **不得根据 `record_code`、`version_no` 或 R3/R4 资料包编号推断批次**；原文没有标注批次名的，同一年度只能算一个批次。
- 同一 `record_code` 下的多个 `version_no` 是版本关系，算**同一批次**，不得误算成多个独立批次。
- 同一年度的 R3、R4 两个包（不同 `record_code`）也按**同一批次**归并；只有原文明确把两包标成不同批次时才拆分。
- 出现两个及以上不同适用年度，或同一年度存在多个原文明确标注的批次，才算多个历史批次。

名称匹配口径：

- 比较前统一去掉首尾空白、大小写归一、全半角归一（NFKC）。
- 实验室别名（如「EDA」「EDA 实验室」「EDA创新实验室」）必须覆盖；别名检索**不得漏掉其他年度或其他批次的相关记录**。
- 命中后要产出**命中的批次标识集合（年度 + 批次名）**，而不是只取一个版本。

**适用年度的判定依据**：

1. 适用年度只能取自资料自身声明的年度信息，**不得用 `published_on` / `effective_on` 代替**；发布日期与生效日期只用于展示与排序。
2. 取值优先级：
   - ① `applicability_raw` 的年度类键：`适用年度`、`适用学年`、`适用届别`（届别需按学年规则换算，换算不确定时按缺失处理）；
   - ② `temporal_notes` 中的年度类键；
   - ③ 标题或 `record_code` 中明确写出的年度（如「2026-2027 学年」「2026 年」）。
3. 解析与归一化沿用规则侧现有年度口径，本文不另立一套；学年区间统一取其起始年作为批次键，原始表述保留用于展示。
4. **缺失**：三个来源都没有年度 → 该资料年度不明，不参与批次归并，不得据此认定「只有一批」；相关问句按证据不足处理。
5. **冲突**：多个来源给出不同年度 → 视为冲突，不采用其中任何一个；该资料不参与批次归并，需人工复核后重新入库。
6. 参与批次统计的只有「年度明确」的资料；年度不明或冲突的资料不计入，也不能用它们补足批次数量。

与 S4-03 的边界：以上放行只服务公开名录与研究介绍。用户没有指定年度、询问自己能否进入实验室时，仍是证据不足，**不追问年度，也不使用历史 R3 条件回答**（S4-03）；明确年度走 S4-22，询问当前走 S4-23。

**资料时效判定（S4-01、S4-02 的依据）**：青禾计划的 R3 招募通知报名截止 2026-10-31，判定为 `expired`；R4 是同一份历史通知所载的方向与介绍，判定为 `historical`。两者都**不是** `current`，所以 S4-01（名录）、S4-02（研究方向）的 `answer_mode` 为 `historical`，回答时须声明「2026-2027 学年通知所载」，不得按现行政策口径表述。S4-03（接收条件）不套用这一放行：未写年度默认证据不足，明确年度才按 `historical`（S4-22），明确当前走 current gate（S4-23）。

**实现层只做到一半，P2 仍是残余风险**：`agent_workflow.py` 的 `_eligible` 已不再要求 `timeliness=current`，已截止招募在「某实验室现在还招吗」这类具名状态问句下能走 `_answer_closed_recruitment` 返回 `historical`。但 `agent_policy_context.py` 的 `_evidence_mode()` 对 `HISTORICAL/EXPIRED` 资料还有一道条件：

```python
if status in _ARCHIVED or ended:
    if not closing_recruitment and (self.current or self.needs_window
            or not (self.historical or self.periods)):
        return None
```

也就是说，**用户既没写年度、也没问历史时，历史资料仍会被判为不可用**。S4-01「学院有哪些实验室」、S4-02「EDA 实验室研究什么」正属于这一类，资料审核通过后仍可能返回证据不足。

**注意：`_answer_closed_recruitment` 是 #59 尚待修复的现存行为，不能当作 S4-24 的目标预期。** 该路径对「某实验室现在还招吗」会返回 `answered` / `historical` 并引用历史通知；而 S4-24 的目标是 `insufficient_evidence` / `insufficient_data`、`citations` 为空、不引用历史通知。两者相反，验收时以 S4-24 的目标为准，修复由吴诗莹在 #59 完成，本文不改工作流代码。

**吴诗莹认可的方向（2026-11-27 已由组长确认）**：仅在同时满足以下条件时，无年度问句可按 `historical` 放行——

1. 问题属于**公开名录或研究介绍**（如「学院有哪些实验室」「EDA 实验室研究什么」）；
2. 用户既没指定年份，也没明确问「现在／当前」；
3. 能确认该事项**只有一个**「已审核、已开放检索、年度明确」的历史批次；
4. 不涉及联系方式有效性、是否仍在招募、实时剩余名额。

放行时回答开头注明年份或批次，并说明这是当时的情况。

**多批次必须追问或拒答**：若存在多个相关历史批次（含同一年度原文明确标注的第一批、第二批），或无法确认只有一个批次，**不得擅自选择**，应先追问用户想查哪一批；本次检索只命中一个年度**不等于**库内只有一个批次，还要按 3.7 的口径核对库内其他符合条件的批次（需要检索层提供按事项统计批次的能力，见 §6）。

**范围外的三类问题不放行**：联系方式是否仍有效、是否仍在招募、实时剩余名额，按 4.4 与 5.2 继续拒答；旧批次材料只能说明该批次的截止情况，不能外推到当前。

**S4-03 接收条件的口径（2026-11-27 确认，选 B：不扩放行范围）**：S4-03 问的是接收条件，属招募信息，不在「公开名录或研究介绍」的放行范围内。按三分法处理：

1. **未写年度、库内只有历史招募通知** → `insufficient_evidence` / `insufficient_data`，**不使用历史 R3 回答，也不追问年度**（S4-03）；
2. **明确写了对应年度** → 只使用该年度已审核、已开放的 R3 资料，`answered` / `historical`，声明年度，并**检查适用年级与专业是否匹配**；仍只解释当年接收对象与条件，不替用户判断是否一定能进入（S4-22）；
3. **明确问「现在／目前／当前」** → 执行 current gate：有已审核的当前通知才按 `current_policy` 回答，没有就 `insufficient_evidence` / `insufficient_data`（S4-23）。

同一函数另有 `len(document_periods) > 1 → None` 的保护：**多个年度资料并存时不得擅自选择其中一个年度**，本设计沿用这一约束，不自行挑年度作答。

严格的限制不因上述放行讨论而放宽：当前联系人、实时招募状态、实时名额对历史资料一律拒答，见 4.4 与 5.2。

**P2 的适用范围（2026-11-28 明确）**：P2 只服务 S4-01、S4-02 这类「无年度的公开名录或研究介绍」。**S4-24「现在是否还招」不属于 P2**，不得用已截止的历史通知回答；历史截止事实只能用于 S4-08「2026 年是否截止」，二者严格分开。

### 4.2 追问口径

| 必问 | 触发条件 | 追问句 |
| --- | --- | --- |
| 1 | 只说「学院有什么资源」，没说哪类 | 你想找的是培养方案与课程、实验室与科研团队、竞赛与科研实践，还是通知与办事渠道？ |
| 2 | 说「实验室」但没说目的 | 你是想了解实验室的研究方向，还是想了解怎么报名进实验室？ |
| 3 | 问培养方案或课程，没说专业或年级 | 你问的是哪个专业、哪一级的培养方案？ |
| 4（例外一） | 问实验室名录或研究介绍，且库内存在多个相关历史批次、无法确定唯一批次（含同一年度原文明确标注的第一批、第二批） | 你想查哪一年度、哪一批（例如 2025 年度，或 2026 年第一批、第二批）？ |
| 5（例外二） | 问历史联系人，且库内存在多个不同年度批次、联系人不同 | 你想查哪一年度的联系人（例如 2025 年度还是 2026 年度）？ |

批次是否唯一要到枚举之后才能判断，因此**例外一的追问发生在枚举之后**，不是检索前的固定追问；具体由 #59 的工作流实现。

明确不问：问「我能不能进」不追问年级与姓名（只答接收条件，不判个人资格）；不追问年度、学期；不追问姓名、学号、学院。

**追问例外（只有两类，2026-11-27 组长确认，2026-11-28 补充同年度批次）**：

1. 公开实验室名录、研究介绍存在多个相关历史批次且无法确定唯一批次时，追问年度或批次（同一年度原文明确标注第一批、第二批的，追问第几批）；
2. 历史联系人存在多个不同年度批次且联系人不同时，追问年度。

其他 S4 场景继续遵循不追问规则。**报名与接收条件不进入这两类例外**：报名按 4.3 的年度口径处理；接收条件按 S4-03、S4-22、S4-23 处理，未写年度且只有历史招募通知时直接证据不足。

### 4.3 过期与历史口径

- 问「某实验室研究什么」「学院有哪些实验室」：历史介绍或名录仍可回答内容，但不得写成「当前正在招募」。
- 问「怎么报名」：过期通知按 `historical` 回答流程，并说明本年度已截止、新年度通知待发布；报名不进入 4.2 的两类追问例外，按本条年度口径处理。
- 问「2026 年报名截止了吗」：按历史口径回答该年度已于 2026-10-31 截止，不下当前结论。
- 问「这个实验室现在还招吗」：没有已审核的当前通知时**不判断当前招募状态**，返回证据不足，不用历史通知回答。
- 问「还剩几个名额」「招几个」：名额、接收人数、考核条件都是当年度信息，**不能跨年沿用**，返回证据不足。
- 资料被新版本替代时，只回答历史问题并说明已被替代；问现行版本而只有旧版时返回证据不足。
- **库内只有单一历史业务批次时**：在满足 4.1 所列条件（公开名录或研究介绍、用户未指定年份也未问当前、单一批次、不涉及联系方式与名额）时，可按该批次作答；回答开头注明年份或批次，并说明「这是当时的情况」。工作流放行机制见 4.1 的 P2 说明：业务口径已确认，工作流实现与回归测试待吴诗莹完成，实现前仍按未满足处理。
- **多个批次并存时**：不得擅自选择其中一个批次作答；名录或研究介绍、历史联系人按 4.2 的两类例外追问年度或批次，其他类型（如报名、接收条件）按各自规则返回证据不足；已写年度/批次则严格匹配。检索只命中一个年度不代表库内只有一批，需按 3.7 的口径核对其他符合条件的批次（含同一年度原文标注的第一批、第二批）。
- **旧批次材料的边界**：只能说明该批次的报名与截止情况，不能外推为当前招募状态、当前联系方式或剩余名额。
- **接收条件（S4-03/S4-22/S4-23）**：未写年度且库内只有历史招募通知 → 证据不足，不使用历史 R3、不追问年度；明确写了年度 → 只使用该年度已审核、已开放的 R3 资料，按 `historical` 回答，声明年度，并检查适用年级与专业是否匹配，仍只解释当年接收对象与条件、不替用户判断能否进入；明确问「现在／当前」→ 执行 current gate，有已审核当前通知才按 `current_policy` 回答，否则证据不足。
- 没有该实验室、没有该类别、或只有未审核资料时，统一回答「目前没有可依据的已审核资料」，不用追问掩盖资料缺口。

### 4.4 联系人的时效判断

实验室联系人属于**年度招募信息**，不是长期公开信息。按问题类型分四种，**不把「无年度」一律推成追问**：

| # | 情形 | 处理 | 目标状态 |
| --- | --- | --- | --- |
| 1 | 问「现在／目前／当前该联系谁」 | 直接证据不足，**不追问年度**——补一个历史年度也回答不了当前问题 | `insufficient_evidence` |
| 2 | 问历史联系人、未写年度，库内只有一份适用年度通知 | 不追问，按该年度回答并声明所属年度 | `historical` |
| 3 | 问历史联系人、未写年度，库内有多份不同年度通知且联系人不同 | 追问年度，不能替用户选一份 | `needs_clarification` |
| 4 | 没有已审核联系人资料，或 `timeliness` 为 `pending` / `uncertain` | 直接证据不足，不追问年度 | `insufficient_evidence` |

判定口径（2026-11-27 与规则侧确认）：

> 未写年度的联系人问题，若库内只有一份适用年度通知，按该年度 `historical` 回答并声明年度；存在多份不同年度且联系人不同则追问年度；问「现在／目前／当前」时直接证据不足，不进入年度追问；无已审核资料或时效待定、不确定时不展示联系人。

补充约束：

1. **禁止表述**：不得说「这是该实验室的联系人」，只能说是「<年度> 通知所载联系人」。
2. **R6 不受本条限制**：学院、系所层面的公开联系方式属于长期公开信息，按 `current` 管理。
3. **在窗口内**：`timeliness=current` 且仍在招募窗口内时，可按 `current_policy` 回答，并标注资料来源与截止日期。
4. **规则侧已覆盖**：`business-rules.md` §7.3 第 7 条限制联系人只能来自 R3 片段，§7.4 对 `HISTORICAL/EXPIRED` 的联系方式在「现在／目前」问句下一律拒绝，与本条一致。
5. **前置条件**：本条受 P2 约束；P2 未满足时，第 2、3 类问题只能返回证据不足，而不是答一个历史联系人。
6. **多年度联系人相同时**：可以合并回答，但必须列出所引用的年度资料（例如「2025、2026 两个年度的通知均为同一联系人」），标记为历史属性，**不得表述为当前联系人**；引用的每个年度都要有对应的 citation。

## 5. S4 功能边界

### 5.1 本轮承诺

1. 按六类回答「学院有哪些资源」，每项给出来源与引用。
2. 回答实验室的研究方向、简介与公开介绍。
3. 按历史口径回答实验室报名流程，并明确本年度已截止。
4. 回答培养方案、课程、选课、辅修与学位要求的现行或历史口径。
5. 给出学院通知栏目与办事入口，以及有官方出处的联系方式。
6. 资料不足、来源不明、时效无法确认时明确拒答并说明缺什么。

### 5.2 明确不承诺

| 不承诺项 | 理由 |
| --- | --- |
| 实时剩余名额（「现在还剩几个」） | 无实时核验数据；**即使招募通知仍为 `current`，计划招收人数也不等于实时剩余余额** |
| 跨年度沿用计划人数 | 计划人数只属于当年度通知，跨年度一律不答（`business-rules.md` §7.4） |
| 实时招募状态 | 只能按通知日期判断「本年度是否已截止」 |
| 未经官方资料支持的导师评价 | 无评价来源，且属主观判断 |
| 自动判断某实验室当前是否招收本科生 | 接收条件为年度信息，且需个人资格判定 |
| 缺乏来源的联系方式与报名条件 | 一律不补造 |
| 按人数或绩点筛选实验室 | 一览表的「接收人数与条件」是自由文本，无法结构化 |
| 个人能否被录取 / 能否进某个实验室 | 只答条件，不代判资格 |

### 5.3 资料缺口

| 缺口 | 影响 |
| --- | --- |
| R6 学院公开信息与联系方式无已审核资料包 | 学院办公电话、地点类问题一律证据不足 |
| R1 学院通知栏目尚未全部入库 | 只能回答已入库栏目，不能保证「所有通知」 |
| R2 仅有历史培养方案（2022 级及更早） | 目标年级方案缺失，只能按历史口径回答 |
| R3/R4 青禾包仍在待审核 | 实验室类问题在审核前一律证据不足 |
| R5 开放探索性实验通知仍为 pending | 该类问题暂不可答 |
| 青禾计划 `deadline_on` 为空 | 入库补 `2026-10-31` 前，规则无法稳定判断「是否已截止」 |
| 无年度历史资料的放行机制（P2 残余） | `_evidence_mode()` 对未写年度的历史资料返回 `None`；业务口径已确认（见 4.1），工作流实现与回归测试待吴诗莹完成，实现前 S4-01、S4-02 在资料审核后仍可能证据不足 |
| 按事项统计历史批次的能力 | 现有接口只能按 UUID 点查，`retrieve()` 受 `top_k ≤ 20` 与同文档多片段排名影响，无法保证覆盖同一主体的全部批次。王智洋已在 PR #60 按方案一实现两个可选只读方法（`list_document_metadata` / `list_parsed_chunks`），**已合并到 main（`4713117`）**，未进公共 Protocol；业务层按 3.7 的批次归并与名称匹配口径使用 |
| 计划人数无实时核验 | 名额类问题（S4-09、S4-15、S4-20）一律证据不足，不提供实时余额 |

### A.4 雷葭雨（2026-11-27）

联系人口径不能简单二选一，按问题类型分四种：

1. **问「现在／目前／当前该联系谁」**：直接返回证据不足，不追问年度——用户问的是当前联系人，补一个历史年度也不能回答当前问题。
2. **问历史联系人、没写年度，库内只有一份适用年度通知**：不追问，按该年度回答联系人，标 `historical`，并在答案中声明所属年度。
3. **问历史联系人、没写年度，库内有多份不同年度通知且联系人不同**：追问年度，不能替用户选一份。
4. **没有已审核联系人资料，或 `timeliness` 为 `pending / uncertain`**：直接证据不足，不追问年度。

### A.6 组长确认（2026-11-27）

组长对 S4-03 与追问例外给出最终口径：

1. **S4-03**：未指定年度 → `insufficient_evidence` / `insufficient_data`，不使用历史 R3、不追问年度；明确指定年度 → 只用该年度已审核、已开放的 R3，标 `historical`，并检查适用年级和专业；明确询问当前 → 执行 current gate，无已审核当前通知则证据不足。即使指定年度，也只解释当年接收对象和条件，不替用户判断是否一定能进入。
2. **§7.2 追问例外只有两类**：公开实验室名录、研究介绍存在多个相关历史批次且无法确定唯一批次时追问年度；历史联系人存在多个不同年度批次且联系人不同时追问年度。其他 S4 场景继续遵循原有不追问规则。
3. **§7.5 的 S4-03 拆成三个独立场景**：默认无年度证据不足（S4-03）、明确年度 `historical`（S4-22）、明确当前 current gate（S4-23）。
