## 一、这份数据是什么

- 文件：[`frontend/src/admin/data/documents.json`](../../../frontend/src/admin/data/documents.json)，共 **44** 条；由 [`frontend/src/admin/mock.ts`](../../../frontend/src/admin/mock.ts) 装载，装载时会校验四个状态值仍在契约枚举内（见 `frontend/src/admin/validate.ts`）。
- **性质：前端内置模拟数据**，不是数据库读取结果，也不是真实核验结论。页面在使用该模拟数据时，必须明确标注其为前端演示数据；切换至真实 API 数据后，应同步更新数据来源提示，不得将真实数据误标为模拟数据。
- 资料名称、资料类别、发布单位、文号、来源链接、发布日期、适用范围、核查说明均取自第二次团队作业已合并的 44 条资料登记：
  - `docs/assignment-02/database-design/sql/02_review_seed_44.sql`
  - `docs/assignment-02/database-design/knowledge-base/入库预览_44条.json`（本次生成所用）
- 四个状态字段的来源分两部分：`seed_status` 保存登记原值，`source_verification_status` 等四个字段是**演示编排**结果，逐条在 `demo_rule` 里写明用了哪条规则。

## 三、状态枚举与界面文字

值严格使用契约枚举，**不新增、不改名**。

| 字段 | 枚举 → 界面文字 |
| --- | --- |
| 来源核验 | `pending` 待核验 / `partial` 部分核验 / `verified` 已核验 / `failed` 核验失败 |
| 时效核验 | `pending` 待核验 / `current` 当前有效 / `historical` 历史参考 / `superseded` 已被替代 / `expired` 已过期 / `uncertain` 时效不明 |
| 正文提取 | `pending` 待提取 / `extracted` 已提取 / `needs_ocr` 需 OCR / `failed` 提取失败 |
| 检索开放 | `blocked` 未开放 / `review_only` 仅审核可见 / `enabled` 已开放检索 |

## 四、演示编排规则

**前提：不降级任何登记值，也不为演示而批量放开检索。**

| 规则 | 适用资料 | 来源核验 | 时效核验 | 正文提取 | 条数 |
| --- | --- | --- | --- | --- | --- |
| R1 | `policy_status = 当前有效` 的三份现行文件 | `verified` | `current` | `extracted` | 3 |
| R2 | `已废止` | 保持原值 | `superseded` | `extracted` | 2 |
| R3 | 扫描件无文本层 | 保持原值 | `pending` | `needs_ocr` | 1 |
| R4 | 通知已过办理/申请期限 | 保持原值 | `expired` | `extracted` | 10 |
| R5 | 历史参考 / 历史版本 | 保持原值 | `historical` | `extracted` | 8 |
| R6 | 当前参考 / 本年度通知 | 保持原值 | `current` | `extracted` | 9 |
| R0 | 其余 | 保持原值 | 保持原值 | 保持原值 | 11 |

检索开放**完全由时效与提取推导**，不使用独立规则：

1. 只有 R1 的 3 条为 `enabled`；
2. 正文 `needs_ocr` 或时效仍为 `pending` → `blocked`；
3. 其余 → `review_only`（审核可见，不进入正式问答）。

这样保证契约的硬约束成立：`retrieval_status=enabled` ⇒ 首版纳入 + 来源 `verified` + 提取 `extracted` + 时效 ∈ {`current`,`historical`,`superseded`,`expired`}。

### 两个刻意保留的"空样本"

44 条登记里**不存在** `failed`（来源核验/正文提取失败）和 `uncertain`（时效不明）的记录。演示数据**不伪造**这两类结果，因此：

- 筛选下拉仍保留这两个选项（枚举完整性）；
- 选中后必须出现**空结果态**，文案写明"当前模拟数据中没有该状态的资料"；
- 空结果态同时作为自动化测试的异常用例。

## 五、契约缺口（需组长罗宇泽确认）

1. **`DocumentSummary` 缺"发布单位/来源"字段。** 契约 `backend/contracts/models.py` 中 `DocumentSummary` 只有 `document_id / title / document_type / category_name / record_code / version_no / 四个状态 / updated_at`，没有 `publisher`，也没有 `source_url`；但任务书明确要求列表展示"发布单位或来源"，数据库 `document_versions.publisher` 已有值。
   → 本轮处理：页面直接展示 `publisher`，并在此处标注缺口；建议 V1.1 为 `DocumentSummary` 增补 `publisher: str | null` 与 `source_url: str | null`。
2. **"修改资料元数据"缺 DTO 与协议方法。** HTTP 层有 `PATCH /api/v1/admin/documents/{document_id}`，但 `DocumentAdminService`（`protocols.py`）只有 `list_documents / get_document / ingest_document / reindex_document`，`models.py` 也没有元数据更新请求模型。
   → 本轮处理：只做按钮与「尚未实现 · 契约未定义元数据更新 DTO」提示，不伪造保存成功。
3. **列表"按状态筛选"的参数名未约定。** 契约只写"可按状态筛选"，未给 query 参数名；`DocumentAdminService.list_documents()` 也只有 `page` / `page_size`。
   → 本轮处理：前端按本地数据筛选，不拼真实请求参数；接入时建议使用 `source_verification_status` 等四个与字段同名的 query 参数，并给协议方法补同样的可选参数。
